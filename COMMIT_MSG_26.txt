CI run 35499194130（develop 037b8c25）红 6 个 job，根因为 **5 个互相独立的
真实缺陷**（非 flake）。逐个定位并本地复现验证如下。

一、admin-web-build / windows-admin-web —— tsc -b 6 处类型错误（同一根因）
  c3fa75d3「10 处设置页 signal 接线」把 useQuery 的 queryFn 改成下发 TanStack
  的 AbortSignal，但**页面内自持的** notificationApi.getChannels 没同步加形参
  （TS2554）；同批新增的 4 个测试文件另有 5 处类型不严：
    · app-deployment-timer-stale-closure：mock 实现签名比接口更严
      （_appId: string vs applicationId?: string）→ TS2345
    · execution-detail-fulllogs-race：querySelector 未给泛型，Element 不可赋给
      HTMLElement → TS2740
    · queries.abort-signal：mock.calls 解构出的 config 可空未收窄 → TS18048×1
      + TS2532×2
  修法：形参补全 / mock 签名对齐接口 / querySelector<HTMLElement> / 加 ?. 收窄
  （断言强度不变——config 缺失时 config?.signal 为 undefined，toBeInstanceOf
  同样红）。**反证**：修复前 `npx tsc -b` 复现全部 6 条错误且行号与 CI 一致；
  修复后 0 error，CI 同命令 `npm run build`（tsc -b && vite build）通过。

二、api-types-drift —— 契约产物漂移
  1edf6b5c 给 pagination.dto 加 @Max(10000)（+ ApiProperty maximum）、
  50486ee3 改 create-silence.dto 的两处 description，**均未重导出 openapi.json**。
  修法：在 WSL 走 CI 同一条导出路径（jest openapi-export.e2e-spec）重导出——
  产出 diff 与 CI 报错**逐行一致**（10× "maximum": 10000 + 2 处描述），随后

  empty-schema 守卫复跑仍通过（6 empty / 48 schemas 全在白名单）。

三、desktop-bundle-drift —— 发布物与源码脱节（最该拦的一类）
  f1cb0d04 只回填了 NETOPT-6⑤ 的哈希，此后**两次改 executor-node/src 的提交
  都没重打 bundle**：
    · c41fd22d（NETOPT-8③）：删除应用时执行器清理 apps/<appId>——新增

  修法：按 ADR-005 同 commit 重打 bundle，本机(Windows) ncc 0.44 产出

四、e2e-full —— 用例 3 的**三个必然失败**叠加（与该用例想验的行为无关）
   ① 任务名用中文「E2E-测试任务-每分钟」，而 TaskFormPage 的 name 字段硬规则是
      `^[a-zA-Z0-9_-]+$`（i18n taskForm.field.name.pattern）→ validateFields
      抛 errorFields，handleSubmit 在校验分支 return，**压根不发 POST**；
   ② 直接 fill `input[id*="cron"]` 就以为设了 Cron——但该输入框由
      `{triggerType==='cron' && …}` 条件渲染，而 initialValues 是 manual，
      **默认根本不存在**（CI 日志里始终没有"设置 Cron"行即为证据）；同理
      entrypoint 是 required 且无默认值，原用例从未填过；
   ③ 提交按钮选择器 /保存|提交|确定/ 先命中同一 Space 里排在更前面的
      「保存为模板」（label 含"保存"），点它只弹模板弹窗，表单永不提交。
  三者叠加下 `formSubmitted` 却按"点了按钮"就置真，于是去断言"任务应该在列表
  里"，把一条必然失败伪装成业务回归。
  修法：ASCII 任务名 + 先选 Cron 触发方式再填表达式/入口文件 + 提交条
  data-testid 内点主按钮；并把提交凭据从"点了按钮"改成**真实观察到
  POST /api/tasks → 201**（未观察到即打印明确提示，不再伪装）。同时如实化
  Monaco 步骤为条件分支（本表单创建态无编辑器，该步历史恒为 false）。

五、selftests → qa05-callback-tier —— 端口自撞 + 失败现场被自己销毁
  CI 时间线：迁移 08:22:06 通过 → 恰好 90s 后 "(fetch failed)"，即 admin-api
  **从未监听**。签名与 EADDRINUSE 完全一致（已用占用端口实测复现：
  fetch failed / cause=ECONNREFUSED / 子进程 exit=1）。但脚本把所有证据都毁了：
    · 三个随机端口各自独立抽取、**互不查重**——实测自碰撞率 0.0335%
      （67/200000，约 2985 次运行撞一次）；撞上即被撞服务静默起不来；
    · waitForHttp 只抛一句 "fetch failed"——该串同时覆盖 ECONNREFUSED（无人
      监听）/DNS 失败/代理拦截，指向完全不同的原因；
    · cleanup 的 rmSync(tmpDir) **删掉唯一的 admin-api 日志**，真机报障时现场
      已被自己销毁，只能靠猜。
  修法：① 端口抽取去重 + 开工前 TCP 预检（环境变量显式指定被占=报错并给出
  lsof 查法；随机抽到被占=**自动重抽**，不让倒霉抽样判红 CI；SKIP_DOCKER 模式
  下 PG/Redis 属外部复用、本就应在监听，故不检）；② 超时路径补齐三件事——
  子进程存活/exitCode/signal、端口 TCP 层结论、admin-api 日志尾部；③ 子进程
  提前退出时不再空等满 90s；④ 失败时**保留**临时目录（成功仍清理）。
  实测：同一 CI 签名现在直接报出 `exitCode=1` + `EADDRINUSE` + 日志尾部，
  且 happy path 仍 10/10 通过。

另（随批）：executions-page.test.tsx 的防抖用例改为"初始加载后再启用 fake
timers 并清计数"，修掉 fake timers 下 findByText 轮询不推进导致的 30s 超时。
