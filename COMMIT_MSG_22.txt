fix(desktop): SDK 发版抢占 GitHub latest——全量装机用户自动更新 404（结构性复发）

客户端报错（v1.5.0 打完后，所有已装机用户）：

    Cannot find latest.yml in the latest release artifacts
    (https://github.com/LuluDeer/AutoCodeFlow/releases/download/v1.5.0/latest.yml)
    HttpError: 404

根因是**设计缺陷，不是偶发**，且每次 SDK 发版都会复发：

1. electron-updater 的 github provider **硬编码**查仓库的 latest release
   （GitHubProvider.js:162 → /releases/latest，配合 releases.atom 首个 entry）。
   它**没有**指定 tag 的入口——`channel` 只改文件名（latest.yml → xxx.yml），
   不改 latest release 的选择。故"同一 repo 内改用具体 release 的 assets"
   这条路走不通（已读源码确认）。
2. round-14 把桌面解耦成独立 `desktop-v*` tag 线，但**两条 tag 线仍共用同一
   个 GitHub Releases 池**。本 workflow 的 `v*` Release 是 SDK 发版产物、
   **0 个资产（不含任何安装包）**，一旦它比 desktop-v* 新就抢占 latest：
       latest        = v1.5.0          (09-19, 0 资产)  ← 客户端查它 → 404
       desktop 真身  = desktop-v1.5.2  (09-17, 14 资产)
   即：**SDK 每发一次版，全量装机用户的桌面自动更新就坏一次**。

修法：GitHub 的 latest 判定**排除 prerelease**。新增 `demote-sdk-release`
job，把本 tag 的 Release 标为 prerelease → 永久退出 latest 竞争 → latest 恒为
desktop-v*（含 latest*.yml），客户端恢复正常。

- 不影响 npm/PyPI：发布物不在 GitHub Releases；
- 不影响 release-please：它以 tag 与 Release 存在性为事实源，prerelease 仍是
  Release（**已实测**：手工把 v1.5.0 标 prerelease 后重跑 release-please，
  仍 success 且无 untagged/aborting）；
- needs 只依赖 version-guard、与 publish 并行：保护窗口越短越好，且即使某个
  publish 失败，latest 也必须已被保护；
- Release 可能尚未创建（时序），故轮询等待 30×2s，仍未出现则 warning 退出
  （不 fail，避免为状态问题阻断发布）；
- 幂等，重跑安全。

已做的止血（本次改动之前的即时动作，保留）：手工 `gh release edit v1.5.0
--prerelease` → latest 回落到 desktop-v1.5.2；已验证 latest.yml /
latest-mac.yml / latest-linux.yml 三个平台全部 HTTP OK。

未采纳的备选（记录以免重复踩）：
- `skip-github-release`：**会连带不打 tag**（action.yml 描述 "do not try to
  tag releases"），而 release.yml 由 tag 触发——启用会彻底断掉发布链路。
  另 manifest.ts 中该开关只出现在"找不到 Release 时用 tag 兜底"的回退分支，
  createReleases 并无跳过逻辑，也不能阻止建 Release。
- 桌面更新迁独立 repo / GitHub Pages：可行但成本高，本修法已足够且更直接。

验证边界：本 job 只在 `v*` tag 推送时运行，无法在 PR 阶段真跑；其实际动作
（gh release edit --prerelease）已在 v1.5.0 上手工执行并验证有效（latest 回落、
三个平台 channel file 可达）。CI 校验 YAML 结构通过（4 jobs / needs 与
permissions 正确）。
