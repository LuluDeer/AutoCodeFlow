fix(api): 审计搜索的 LIKE 元字符未转义 + action 白名单过严（API-09）

两个问题都在 `audit.service.ts`，且共用同一处判据：

① **LIKE 元字符未转义（真实缺陷）**。`username` 过滤直接拼 `` `%${input}%` ``。
   而 ILIKE 里 `%` = 任意字符、`_` = 任意单字符：
     · 运维搜真的含下划线的用户名（如 `zhang_san`）→ 那个 `_` 变通配符，
       **命中 `zhangXsan` 这类无关账号**；
     · 搜 `%` → 命中全部行。
   结果集看起来"能用"，只是多了不该有的行——用户很难察觉，会据此得出错误的
   审计结论（"这个账号在这次操作里出现过"）。这是审计场景里性质最差的一类：
   **多给证据**比少给证据更容易误导。

② **`action` 的白名单过严（体验缺陷）**。原要求 `^[a-zA-Z0-9_.\-\s]+$`，
   否则 400「Invalid action parameter」。但注入风险从来不由白名单承担——
   `action` 一直是**绑定参数**（值从不拼进 SQL），该白名单对安全没有增量，
   只剩副作用：用户想按中文、`:`、`/` 这类正常词搜索时直接吃 400 + 英文技术
   报错，而期待的是"没有匹配"或结果列表。

修法：新增导出的 `escapeLikePattern()`（**先**转义 `\`，再转义 `%` 与 `_`
——顺序不能反，否则会把刚加的转义符再转一次），`action` / `username` 两处共用；
`action` 白名单放宽为只限长度（保留 `slice(0,100)` 的 DoS 防护）。
两条路径（findAll / exportCsv）保持同一判据（R4 P1-2 的 parity 要求）。

**安全性说明**：这不是放宽安全。旧白名单挡的是"特殊字符"，而真正可被利用的
LIKE 元字符它**没挡**（`_` 与空格都在白名单里，`username` 分支更是完全没有
白名单）。改后所有值一律绑定 + 转义，语义严格更强。

验证：admin-api 3036 passed / 185 suites；tsc --noEmit 0 error；eslint 0 error。
反证 11 条（audit-like-escaping.api09.spec.ts），已实测两向都红：
  · 改回裸插值（去掉 username 的转义）→ 1 条红；
  · 把白名单加回去 → 1 条红。
另改写 3 条**钉住旧行为**的既有用例（`rejects invalid action characters` 等）：
它们断言"含特殊字符必须 400"，正是被有意放宽的那条判据；现改为断言
"不 400、转义后按字面量绑定"，并覆盖 `%`/`_` 的转义结果与两路径一致性。

写守卫时踩到的坑并已修正：守卫读源码时**必须剥注释**——本文件的头注与源码
注释里都引用了旧写法（`%${input}%`、旧白名单正则）作反例说明，不剥注释会把
"解释缺陷的注释"当成缺陷本身，红得毫无线索（本轮已第二次踩到，已写进注释）。
