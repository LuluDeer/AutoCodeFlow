## P1（8 条）

### 安全域

#### E-P1-S1 任务调度态写面（trigger/pause/resume/batch）默认放行「任何登录用户操作任意项目任务」
- **证据**（读码确认）：
  - `apps/admin-api/src/modules/task/task.service.ts:722-732`（`assertCanOperate`）：项目非成员 resolveRole 返回 `null`，函数**仅在 `role === "viewer"` 时抛 403**，`null` 穿透放行。
  - `task.service.ts:795-803`：`isOperateScopeOwner()` 读 `taskScope.operate`，未配置时 `false` → 走宽松 `any`；只有显式 `TASK_OPERATE_SCOPE=owner` 才叠加属主/项目 editor 校验。
  - 触达端点：`task.controller.ts:570-575/921-926/955-960` 与 `task-batch.controller.ts:48/91/129`、`task.controller.ts:188/235/280`（scope 均为 `project-role`）。
- **影响**：普通登录用户（非成员）可 trigger/pause/resume 任意项目任务，扰乱他人流水线、消耗执行器资源。代码注释自承为已知设计（ADR-013），当前默认即为放行态，按可利用状态计 P1。
- **改法**：生产配置 `TASK_OPERATE_SCOPE=owner`；或把默认值从 `any` 翻成 `owner`。成本小。

### 可靠与数据域

#### E-P1-R1 scheduler 全量加载 active tasks 无分页/上限
- **证据**（推演未实跑）：
  - `scheduler.service.ts:885-888`（staleScanWindowMs）：`taskRepo.find({ where:{status:ACTIVE}, select:["id","timeout"] })` 无 take。
  - `scheduler.service.ts:924-929`（reloadActiveTasks）：同样无 take。
- **影响**：active tasks 万级以上时每分钟全量扫表到内存。
- **改法**：keyset 分页或 take 循环；staleScanWindowMs 可改 `ORDER BY timeout ASC LIMIT 1`。成本低。

#### E-P1-R2 AppDeployment 无乐观锁，read-modify-write save 存在丢失更新
- **证据**（推演未实跑）：
  - `app-deployment.entity.ts:70-143` 无 `@VersionColumn()`（对照 task-exution.entity.ts:234、executor.entity.ts:156 有）。
  - `app-deployment.service.ts:1136/1206/1240/1365/1415/1436/1460/1483/1933/2095/2338` 均为 findByIdRaw → 改字段 → save。
- **影响**：心跳更新与用户 stop/upgrade/灰度并发时，后写 save 覆盖先写。
- **改法**：加 `@VersionColumn()`（需迁移）；或心跳改条件 UPDATE。成本中（架构级，若不动迁移则列为方案建议）。
- **分片4 注记**：方案建议，未改——需数据库迁移（加 @VersionColumn），超出本分片「脚本/文档/仓库卫生」范围。

#### E-P1-R3 app-deployment stale sweep 批量 UPDATE 缺状态条件
- **证据**（推演未实跑）：`app-deployment.service.ts:1726-1731`：`.update(AppDeployment).set({status:FAILED...}).where("id IN (:...ids)")`——无 `AND status='pending'` 条件。
- **影响**：刚被并发心跳改 RUNNING 的行仍会被 sweep 覆盖成 FAILED。
- **改法**：`.where` 追加 `andWhere("status = :expectedStatus", ...)`。成本极低（2 行）。

#### E-P1-R4 cron 定时器回调无 re-entry 保护（fixed_rate 有，cron 漏了）
- **证据**（推演未实跑）：`scheduler.service.ts:1274-1284`（cron 分支）无 `runningTasks.get(taskId)` 检查（对比 `:1238-1258` fixed_rate 有）。
- **影响**：enqueue 超周期时重复触发 DB 查询与锁竞争（不会重复入队，enqueue 有双保险）。
- **改法**：cron 回调开头加与 fixed_rate 相同的 runningTasks re-entry 保护。成本极低（3 行）。

### 前端域

#### E-P1-F1 `maxRetry` 表单下限与后端冲突，编辑态把「不重试」静默钳成「重试一次」
- **证据**（代码级确证；钳位行为推演未实跑）：
  - `apps/admin-web/src/pages/TaskFormPage.tsx:1630-1631`：`InputNumber min={1} max={10}`。
  - 回填 `:447` `maxRetry: task.maxRetry ?? 3`（`0 ?? 3 === 0`，0 被保留）。
  - 后端 `create-task.dto.ts:193-196` `@Min(0) @Max(10)`；`task.service.ts:1322-1323` `attempts: Math.max(1, task.maxRetry ?? 1)`——0 是被后端明确定义需守卫的合法值。
- **影响**：与上轮已修 timeout（P0-6）**同类静默钳位**——打开 maxRetry=0 存量任务不动直接保存，「不重试」被改成「重试一次」。
- **改法**：`maxRetry` 改 `min={0}`；补「编辑 maxRetry=0 不被钳成 1」回归用例。成本极小。

### 脚本/协议域

#### E-P1-P1 控制面 commandId 运行时未执行生成 schema 规定的字符白名单
- **证据**（已实读代码 + grep）：
  - `apps/executor-node/src/commands.ts:97-114` `parseControlCommand()` 手写校验，commandId 只查非空字符串（L102）；生成契约 `generated/protocol.schemas.ts:87` 规定 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`。
  - `ControlCommandSchema` 仅在测试中被 import，pull 取件运行时路径从不使用生成 zod schema。
- **影响**：协议层字符/长度约束在执行器侧被静默放宽。当前 commandId 仅用于日志与回显（不进路径/URL），无 RCE 面，但中台按协议假设字符集关联匹配会对不上。
- **改法**：pull 路径改用 `ControlCommandSchema.safeParse(raw)`（对齐 execute.ts:607 对 ExecuteRequest 的做法）；加「畸形 commandId 被丢弃」用例。成本小。

#### E-P1-P2 根目录 10 个提交草稿文件被 git 跟踪
- **证据**（实跑 git ls-files）：`COMMIT_MSG_18.txt`…`COMMIT_MSG_27.txt` 全部入库，内容为 release-please 排障草稿。
- **影响**：污染仓库根与新人认知。
- **改法**：`git rm --cached COMMIT_MSG_*.txt` + 加入 `.gitignore`。成本极小。
