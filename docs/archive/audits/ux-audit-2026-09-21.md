## 一句话结论

底层工程质量明显高于同规模项目（调度状态机、zip 安全闸、灰度租约、幂等与并发处理都有生产故障复盘注释）。
**问题高度集中在"最后一公里"**：状态机做得极细，但把状态**翻译给用户**的那一层严重缺失。

本报告 **44 条**发现里有 **13 条**属于同一个母题：

> **系统知道真相，但用户看到的是「成功」或「未知」。**

三种形态：① **谎报成功**（做了没事/其实没生效）；② **静默改写**（用户没动的东西被改掉）；
③ **静默丢弃**（用户做过的选择在链路上蒸发）。

第 4 路审计还独立收敛出**同源的第二种母题**，值得单列：

> **已发生的失败被解释得很好，未发生的执行（pending）几乎无解释。**

失败原因 12 类全部有中文本地化标签 + 可执行 runbook——但"**为什么没跑**"（排队？没有可用执行器？
执行器没取件？被维护窗口挡住？）在界面上**一个字都没有**，调度决策（`poolSize`/`afterFilters`/`topRunners`）
只存在于后端日志。用户能回答"为什么失败"，**回答不了"为什么没跑"和"为什么派到那台"**。

**特别值得注意的一条**：pull 模式（ADR-016，NAT 场景唯一可用路径）在安装向导里**完全缺失**——
`ExecutorInstallWizardPage.tsx` 与 `scripts/install.sh` 的 pull 引用数均为 **0**，而
`executor.service.ts` 有 **51** 处。NAT 内的机器按官方向导装完会显示"在线"、向导打绿勾，
但中台入站请求永远到不了它。**照着官方引导做，会得到一个必然失败的拓扑。**

### P0-1 编辑任务的 Glue 编辑器不回填源码，改一次语言下拉即不可逆清空脚本
- **证据**（已复验）：
  - `apps/admin-web/src/pages/TaskFormPage.tsx:1649` — `<GlueEditor taskId={glueTaskId} taskRuntime={savedRuntime} />`，**未传** `initialSource`/`initialLanguage`
  - `apps/admin-web/src/components/GlueEditor.tsx:39,45` — `useState(initialSource || '')` / `setSource(initialSource || '')` → source 恒为 `''`
  - `apps/admin-web/src/components/GlueEditor.tsx:132` — `onChange={(v) => { setLanguage(v); setDirty(true); }}` → **只换语言就启用「保存」**
  - `apps/admin-web/src/components/GlueEditor.tsx:110` — `await tasksApi.updateGlue(taskId, source, language)` → 用空串覆盖
  - `apps/admin-api/src/modules/task/task.service.ts`（updateGlue）— `t.glueSource = source`，**无任何校验**，空串照收；同时 `t.gitRepo = null` 且 `codeSource = GLUE`
  - 对照正确写法：`TaskDetailPage.tsx:590-595` 传了 `initialSource`/`initialLanguage`
- **影响**：编辑任何已有 glue 任务 → Monaco 显示空白（用户第一反应"脚本没了"）→ 顺手点一下语言下拉再点保存 → 真实脚本被 `""` 覆盖，且**任务代码来源被改写成 glue、gitRepo 被清空**。无二次确认、无撤销（只能翻版本历史）。
- **改法**：TaskFormPage 编辑态把 `task.glueSource`/`task.glueLanguage` 存入 state 并传入；**不要**用 `savedRuntime` 兜底 language（会把 javascript 脚本错误回填成 python）。**小**

### P0-3 删除应用不告知任何级联后果，引用它的任务被静默摘掉代码来源

### P0-4 删除应用后的任务失败被分类为「未知原因」，而真实原因系统完全知道

### P0-8 pull 队列超时后任务被静默丢弃，最终归因为「未知原因」
- **证据**（已复验）：
  - `apps/admin-api/src/modules/executor/executor-pull.service.ts:291-296` — 过期载荷仅 `logger.warn` 后 `continue`，**不做任何执行行终态化**
  - `apps/admin-api/src/modules/scheduler/scheduler.service.ts:728-738` — 「从未被派发」桶写死 `failureReason: ExecutionFailureReason.UNKNOWN`（`:725` 注释自承"本桶只回收「从未被派发」的行"）
  - 对照：**同一次 sweep 的另一个桶已经修好了** —— `:604` 用 `STALE_RECOVERED` 取代了 `UNKNOWN`（`:597` 注释："使『sweep 恢复 + 重试预算兑现/耗尽』全链路可溯源"）
  - `zh.ts:1680-1681` — `'未知原因' / '查看错误信息和执行日志定位根因。'`
- **影响**：执行器离线/长期不取件时，dispatch **已成功占坑**并把执行行置 RUNNING，载荷超时被丢。用户最终看到「未知原因 + 去翻日志」——**而这条任务从未在任何机器上运行过，根本没有日志可看**。误导性分类把排查方向指向一个不存在的东西。
- **额外价值**：这不是"漏了一个分类"，而是**同一类失败按被哪个桶捡到而有不同分类**（:604 是 STALE_RECOVERED、:735 是 UNKNOWN）。既有修复先例就在同一个函数里，补 `NEVER_DISPATCHED` 是收口而非新增设计。
- **改法**：① `takeTask()` 丢弃处按载荷里的 `executionId` 反查并终态化（注意与 sweep 的双写竞态，用 `transitionToTerminal` 的 winner 语义兜底）；② 至少把 `:735` 的 `UNKNOWN` 改为可区分值（`NEVER_DISPATCHED`）+ runbook「执行器未在 TTL 内取件」。**中**

### P0-9 安装向导只能装出 push 模式执行器，NAT 场景在 UI 上完全不可达
- **证据**（已复验）：
  - `apps/admin-web/src/pages/ExecutorInstallWizardPage.tsx` — 全文 **pull 引用数 = 0**（`INSTALL_ENV_KEYS` 仅 `ADMIN_API_URL`/`EXECUTOR_SHARED_TOKEN`/`EXECUTOR_ADDRESS_PUBLIC`/`APP_NAME`）
  - `scripts/install.sh` — 全文 **pull 引用数 = 0**（只解析 `--api-url/--secret/--name/--port/--runtime`）
  - 对照：`apps/admin-api/src/modules/executor/executor.service.ts` — pull 引用数 **51**
  - 唯一开关：`apps/executor-node/src/config.ts:246` `pullMode: process.env.EXECUTOR_PULL_MODE === 'true'`
- **影响**：NAT 内机器按"官方安装向导"装完 → **注册成功、列表显示在线、向导第 5 步打绿勾**，但中台入站 POST 永远到不了它。任务派给它后永不执行，只能等 stale sweep 在 `max(2×timeout, 60s)` 后判失败（并落入上一条的 UNKNOWN）。用户在向导里被引导到一个**必然失败的拓扑**，且向导的排查清单里没有 NAT/pull 这一项。
- **改法**：向导加"网络模式"选择 + `INSTALL_ENV_KEYS` 加 `EXECUTOR_PULL_MODE` + `install.sh` 加 `--pull` + 排查清单补 NAT 条目。**中**

### P1-22 安装向导第 5 步在基线拉取失败时，会让"任何在线执行器"都算新装成功
- **证据**：`ExecutorInstallWizardPage.tsx:341-349` — `try { knownIds = ... } catch { /* 保持空集合（宽松兜底） */ }`；判据 `:94-99` `findNewlyOnlineExecutor` = 「online 且不在 knownIds」
- **影响**：该函数存在的**唯一目的**就是防"把已有执行器误判成新装的"（`:84-92` 注释自承"这个缺陷没有任何守卫"）。基线拉取失败 → 基线退化为空集 → 守卫失效。在已有在线执行器的机队里，`GET /executors` 一次瞬时失败就会让第 5 步在 5s 内打绿勾并**印出另一台机器的名字和地址**。而"网络不健康"恰是安装最可能失败的条件——**误报成功比 60s 超时更糟**。
- **改法**：基线拉取失败时不推进（显示重试），或标 `null` 并显式提示"无法建立基线，检测结果可能是误报"。**小**

### P1-23 执行器详情页状态是永不刷新的冻结快照，却紧挨「每 30s 轮询」标签
- **证据**（已复验）：`queries.ts:332-338` `useExecutorDetail` **无** `refetchInterval`；紧邻的 `:342-351` `useExecutorMetrics` **有** `refetchInterval: 30_000`；`ExecutorDetailPage.tsx:133` 注释自承"详情页无 refetchInterval，最长滞后 30s"，而 `:477` 却渲染「每 30s 轮询」文案
- **影响**：`status`/`lastHeartbeat` 只来自那一次拉取。**节点刚死，页面可以永远显示"在线"；节点已恢复，页面永远显示"离线"**。而用户打开详情页恰恰是为了诊断这台执行器，读到的可能是几小时前的状态。
- **改法**：`useExecutorDetail` 加 `refetchInterval: 30_000`。**小**

### P1-24「为什么离线」不可回答：判死阈值从不显示，优雅下线与超时判死不可区分
- **证据**：`ExecutorDetailPage.tsx:110` `heartbeatTimeoutMs` 取到手**只用于染色**（`:234-236`），数值从不渲染；离线提示是通用文案（`zh.ts:1174`）

- **改法**：Alert 带上阈值 + 绝对最后心跳时刻 + 已静默时长。**中**

### P1-25 日志分级过滤视图静默截断在 2 万行，而截断告警恰在此视图被抑制
- **证据**：`ExecutionDetailPage.tsx:575` `const { lines: all } = await fetchAllLogLines(value, FULL_LOGS_MAX_LINES)` — **丢弃 truncated**；`:447` `logsTruncated = filteredLogs === null && fullLogs === null && ...` — 截断告警被硬门控在"无过滤视图"
- **影响**：两条独立的静默截断路径叠加。用户按级别过滤后读到一份**看起来完整、实则缺尾部**的日志，而堆栈与致命错误行**就在尾部**。这正是"任务失败找不到原因"的现场。
- **改法**：解构 `truncated` 并用独立 state 承载；告警改为"任一视图截断即渲染"。**小**

### P1-26「重新触发」静默丢弃本次执行的参数，并立刻导航离开现场
- **证据**：`ExecutionDetailPage.tsx:604-615` `await tasksApi.trigger(taskId!)` — **不传 params**（而 `api/tasks.ts:460-461` 的 `trigger(id, params?)` 支持），随后 `nav()` 离开
- **影响**：按钮叫"重新触发"、位于失败定位卡片里，用户合理认为它复现**这一次**执行，实际以任务**当前默认参数**重跑。参数相关失败（如某次带特定入参的补跑）根本复现不了，且用户无从得知；`nav()` 又让用户正要读的错误与日志随页面消失。
- **改法**：触发前告知参数差异，不自动导航。**中**

### P1-27「被覆盖取消」与「被策略 kill」在 UI 上无任何解释
- **证据**：`failure-runbook.ts:113-114` `FAILURE_CARD_STATUSES = ['failed','timeout']`（注释断言"killed 无排障价值"），而同文件 `:68-70` **已经写好了** killed 的动作文案（成为死代码）；`cancelled` 在 `FAILURE_RUNBOOK_ACTIONS`（`:35-79`）中**根本没有条目**；`cancelled` 来自自动覆盖策略 `scheduler.service.ts:1058-1066`（`"Task was covered by new trigger"`，`blockStrategy=COVER_EARLY`）

- **改法**：把 killed/cancelled 加入 `FAILURE_CARD_STATUSES`（killed 文案已就绪）+ 给 cancelled 补 runbook。**小**
