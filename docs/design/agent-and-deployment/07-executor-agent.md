# 07 · 执行器 Agent：通用自主智能体（可行性分析与设计）

> 你的设想：**执行器上跑的不是固定脚本，而是一个通用 agent**——它读 SOP，看这台机器上有什么，自己决定用什么方式实现自动化，自己写、自己跑、自己改到能用，然后回报中台。
>
> 本文回答：**这个设想能不能做？代价是什么？怎么做才不失控？**

## 1. 结论先行

**能做，而且这是整个方案里最有价值的部分。** 但有三条硬约束必须先说清楚：

| # | 结论 | 影响 |
|---|---|---|
| 1 | **「通用」指的是决策通用，不是权限通用** | 工具集仍要封闭枚举，不能给它任意 shell |
| 2 | **它必须新增一个运行时**，不能塞进现有 executor-node | executor-node 是「部署 + 起进程」，没有 agent 循环、没有浏览器 |
| 3 | **它与你现有的安全模型正面冲突**，需要重画信任边界 | 现有 SEC-01/env-whitelist/shell 校验都是为「跑已知脚本」设计的 |

第 3 条是本文的重点——**这个设想的最大风险不是技术难度，是它要求你把「执行器上可以跑任意代码」变成合法状态**。这与你项目里反复加固的方向相反，必须显式决策。

## 2. 为什么这个设想是对的

### 2.1 它解决了 SOP 的根本困境

回顾 [04](./04-sop-protocol.md)：如果 SOP 必须写明「用 Playwright 打开 X 页面、点 Y 按钮」，那么：

- SOP 作者（中台 Agent）必须**预先知道**目标系统的实现细节
- 目标系统页面一改，**所有 SOP 全部失效**
- 中台 Agent 无法验证它写的 SOP 是否可行（它看不到那台机器）

**通用执行器 Agent 把这个困境解开了**：SOP 只描述**目标 + 验收**，实现方式由现场那个能看见屏幕、能试错的 Agent 决定。

```
SOP（中台写）        ：每天早上 9 点把昨天销售报表导出到共享盘
执行器 Agent（现场决）：这台机器有 Chrome → 我用 Playwright
                      这个系统是 C/S 客户端 → 我用 pyautogui 点 GUI
                      它其实有 API → 我直接调 API（最稳）
```

**这是「声明式 SOP + 命令式现场实现」的分工**，与 Kubernetes（声明期望状态、控制器自行达成）是同一个思想。你的直觉是对的。

### 2.2 它让「AI 写应用」真正闭环

原设计（[04 §3](./04-sop-protocol.md)）里，中台 Agent 写完应用要上传给执行器跑。但「在这个特定机器上能跑通」这件事，中台**没有能力验证**。

通用执行器 Agent 补上了这个验证环：它能**在真实环境里试**，试不通就改，改到通为止。这才是「自动化」而不是「生成代码然后祈祷」。

## 3. 核心冲突：与现有安全模型的正面矛盾

这是本文最重要的一节，请仔细看。

### 3.1 现有模型：执行器只跑「已知的、打包好的」代码

你项目里已经建立的信任边界（我逐条核对了代码）：

| 机制 | 位置 | 作用 |
|---|---|---|
| 应用必须打包上传 | `executor-package` + `deploy.ts` | 经过 zip bomb 检查（SEC-05）、病毒扫描 |
| 环境变量白名单 | `env-whitelist.ts` SEC-01 | 子进程只拿到白名单变量，**绝不含执行器密钥** |
| shell entrypoint 校验 | `deploy.ts::validateShellEntrypoint` | 拒绝含空白的命令串，防「`sh -c id`」式任意命令 |
| 部署路径校验 | `deploy.ts` path token 校验 | 拒绝 `..` 路径穿越 |
| 每应用独立 venv | `<appRoot>/releases/<key>/.venv` | 依赖隔离，不污染系统 |
| 控制命令封闭枚举 | `commands.ts` | 「绝不接受中台下发的自由路径」 |

**这套模型的核心假设是：代码是「预先审查过的产物」，执行器只是执行器。**

### 3.2 通用 Agent 要求：执行器要能「现场生成并执行代码」

通用 Agent 的工作方式是：

```
观察环境 → 决定方案 → 写代码 → 执行 → 看结果 → 改代码 → 再执行 ...
```

**这个循环的每一步都与现有模型冲突**：

| 冲突 | 现有 | 通用 Agent 需要 |
|---|---|---|
| 代码来源 | 打包上传、经审查 | **运行时生成**，无人预先看过 |
| 执行方式 | 固定 entrypoint | **任意代码执行**（Python/JS/shell） |
| 依赖 | 上传时声明 | **运行时决定并安装**（`pip install` 现场发生） |
| 迭代 | 一次部署一份 | **高频写-跑-改** |
| 审计 | 部署记录 | 需要**每次生成的代码快照** |

**必须明确的判断**：这不是"加固一下就行"，而是**在受控主机上开启任意代码执行**。这个决定必须你做，且要写进 ADR。

### 3.3 为什么风险可控（如果你按本文的边界做）

关键在于：**Agent 生成的代码，执行边界不应该是「这条主机」，而应该是「一个沙箱」。**

```
❌ 错误设计：Agent 生成代码 → 直接在主机上跑
✅ 正确设计：Agent 生成代码 → 落盘为「候选应用」→ 经既有通道部署 → 在既有边界内跑
```

也就是说：**通用 Agent 负责「写」，既有执行器负责「跑」**。这样：

- 生成的代码仍然走 `deploy.ts` 的既有校验链
- 仍然在 env-whitelist 边界内
- 仍然有 `.venv` 隔离
- **但 agent 的迭代循环里需要「试跑」**——这是唯一需要新增的能力，且必须沙箱化

### 4.1 为什么是新增 `apps/executor-agent` 而不是改 executor-node

| 理由 | 说明 |
|---|---|
| 职责不同 | executor-node 是「执行已知任务」，新 Agent 是「生成未知方案」——混在一起会让既有边界模糊 |
| 依赖不同 | Agent 需要 LLM 客户端、浏览器自动化（Playwright）、更强的文件操作 |
| 生命周期不同 | Agent 是交互式长任务（分钟~小时），executor-node 是任务式（秒~分钟） |
| **爆炸半径** | 分开放，Agent 失控不波及任务执行主链 |
| 部署形态 | Agent 可以只装在「需要 AI 造应用」的机器上，不必全量铺开 |

**但两者部署在同一台机器，共享 `WORK_DIR`**，这样 Agent 生成的候选应用能直接被本地 executor 跑。

### 4.2 与 executor-desktop 的关系（★ 已定案：内置进 desktop）

**你已决策：Agent 功能只加在客户端执行器（executor-desktop）上；python / node 执行器保持纯净，只跑自动化应用、零行为变化。**

因此本方案改为**内置进 `executor-desktop`**，不再新增独立包。理由（你这一版比我原提议更好）：

- 少一个部署单元
- 复用 desktop 已有的**子进程托管能力**（`executor-process.ts` 已会 spawn/监控/重启 `executor-node`，Agent 走同一套模式）
- 复用 desktop 已有的 **IPC 白名单 + 路径域校验**（`ipc-and-security.md`）
- desktop 已是 Electron，**Chromium 内嵌**且 `@playwright/test` 已在 `devDependencies` —— 浏览器能力几乎免费
- 用户能在托盘看到 Agent 状态（透明性）

**Agent 以独立子进程形式运行**，由 desktop 主进程托管（与 executor-node 同款模式），避免重计算卡住 Electron 主进程 UI。

完整分工与新增的安全冲突见 [08-executor-agent-scope.md](./08-executor-agent-scope.md)。

## 5. 沙箱：必须解决的核心问题

Agent 要「试跑」生成的代码，就必须有沙箱。三种强度：

| 方案 | 隔离手段 | 强度 | 代价 |
|---|---|---|---|
| **L1 · 同机受限目录** | 限定 cwd + env 白名单 + 路径校验 | 弱 | 低。能防误操作，防不住恶意代码 |
| **L2 · 容器沙箱** | `docker run --network=none --read-only` 等 | 中 | 中。需要机器有 Docker |
| **L3 · 微虚拟机** | Firecracker / gVisor / Windows Sandbox | 强 | 高。部署复杂度大幅上升 |

**务实建议：L1 为主（因为你要求"在所在电脑上"操作真实软件）+ 关键动作 L2 兜底。**

理由很重要：**你的场景本质上要求 Agent 操作「真实的、本机的、已登录的软件」**（内部系统、Office、客户端）。这类操作**天然无法放进容器**——容器里没有用户的登录态、没有那个内部系统的网络可达性。

所以沙箱在这里的作用**不是防恶意代码，而是防误操作**：

| 沙箱要防的 | 手段 |
|---|---|
| Agent 误删用户文件 | 文件操作限定 `WORK_DIR/agent-workspace/` |
| Agent 误改系统配置 | **禁止**系统级命令（封闭枚举） |
| Agent 访问不该访问的域名 | 域名白名单（SOP 的 `constraints.allowedDomains`） |
| Agent 无限循环 / 烧资源 | 迭代次数 + 时长 + CPU/内存上限 |
| Agent 泄露凭据 | env 白名单（复用 SEC-01）+ 输出脱敏 |

> ⚠️ **必须向你说明的诚实结论**：如果 Agent 能操作本机已登录的浏览器/客户端，那么**它天然拥有该用户的权限**。这不是设计缺陷，是这个需求的固有属性。可做的是「限制它能做什么动作 + 全程留痕 + 关键动作需批准」，而不是假装它被沙箱关住了。

## 6. SOP 的角色必须调整（重要）

原设计（[04 §1.1](./04-sop-protocol.md)）的 front-matter 里有 `requiredTools`，现在需要**大幅弱化**：

| 字段 | 原设计 | 通用 Agent 下 |
|---|---|---|
| `requiredTools` | 指定执行器用哪些工具 | **改为「能力声明」**：`capabilities: [browser, gui, filesystem, http]`——描述**允许的能力域**，不指定具体工具 |
| `acceptance` | 机器可执行验收 | **更重要了**——这是 Agent 唯一的目标锚点。SOP 不规定怎么做，验收就是唯一约束 |
| `constraints` | 边界 | **更重要了**——实现自由了，边界必须更硬 |
| Markdown 正文 | 步骤说明 | **从「操作手册」变为「上下文说明」**：业务背景、已知坑、历史经验 |

### 6.1 SOP 写法对比

**旧（命令式，脆弱）**：
```markdown
### 步骤 2 · 导出报表
1. 打开 https://report.internal.example.com
2. 点击左上角「报表」菜单
3. 在弹窗中选择「昨日」
4. 点击「导出」按钮（id=export-btn）
```
→ 页面一改就废。

**新（声明式，稳健）**：
```markdown
## 要做什么
把「昨日」的销售报表导出到 \\shared\reports\daily\ 目录。

## 验收
- 目标目录出现文件，文件名含昨日日期
- 文件是有效的 xlsx（能被 openpyxl 打开）
- 文件行数 > 0

## 已知情况
- 报表系统有 Web 版和 C/S 客户端，**Web 版更稳，优先用它**
- 导出偶发超时，重试一次通常能成
- 登录需要 2FA，但可以用「信任此设备」跳过

## 你不必照做
上面没说怎么实现。你可以写 Playwright、可以用 pyautogui、
如果发现它其实有 API 就直接调 API——**以验收通过为准**。
```

**最后一段是关键**：明确告诉执行器 Agent「你有实现自由」。这才叫通用 Agent。

## 7. 迭代循环设计

```
执行器 Agent 会话（kind: sop_execute）
    │
    ├─ ① 感知：探测本机环境（有哪些工具可用？目标系统什么形态？）
    │      → 产出 environmentReport（回传中台，也可作为澄清依据）
    │
    ├─ ② 规划：读 SOP → 选择实现路径 → 产出候选应用骨架
    │
    ├─ ③ 试跑：在 workspace 里跑候选代码（沙箱内）
    │      · 观察输出 / 截图 / 错误
    │      · 不通过 → ④
    │
    ├─ ④ 诊断：为什么失败？（环境问题？代码 bug？SOP 不清？）
    │      ├─ 代码 bug      → 改代码 → 回 ③（最多 N 轮）
    │      ├─ 环境缺失      → 尝试安装/降级方案 → 回 ③
    │      └─ SOP 不清楚    → ★ 发起澄清 → 中台 Agent 答复/修订 SOP → 回 ②
    │
    ├─ ⑤ 验收自检：跑 SOP 的 acceptance
    │      · 全绿 → ⑥
    │      · 失败 → 回 ④
    │
    └─ ⑥ 交付：打包候选应用 → 走既有 executor-package 通道部署
           → 回报中台 Agent（附：environmentReport / 实现说明 / 验收结果）
                → 中台独立复验 → 通过则上线
```

### 7.1 硬闸门（必须）

| 闸门 | 默认 | 违反后果 |
|---|---|---|
| 单次迭代最大轮数 | 15 | 终止 + 上报「无法在合理轮次内完成」 |
| 单会话墙钟上限 | 2 小时 | 终止 |
| 澄清轮次 | 5（与中台协商，见 [04](./04-sop-protocol.md)） | 转人工 |
| 试跑次数 | 30 | 终止 |
| 依赖安装次数 | 10 | 终止（防依赖地狱） |
| CPU / 内存 | 可配上限 | 超限终止 |

### 7.2 为什么 ⑥ 要走既有通道而非直接跑

**这是安全设计的关键一笔**：Agent 生成的代码**不直接在你机器上长期运行**，而是：

1. 打包成标准应用包
2. 走 `executor-package` 上传（经过既有 zip bomb / 病毒检查）
3. 走 `deploy.ts` 部署（经过 shell 校验、路径校验）
4. 在 env 白名单边界内运行

这样 Agent 的"自由"被限制在**生成阶段**，运行阶段仍受既有纪律约束。

## 8. 澄清循环的升级（回到你的核心诉求）

结合 [04 §3 ④](./04-sop-protocol.md)，通用 Agent 让澄清循环更丰富：

| 执行器 Agent 遇到 | 澄清类型 | 中台 Agent 处置 |
|---|---|---|
| SOP 没说清要哪种报表 | `ambiguous` | 补充细节 → 修订 SOP |
| 本机没有 Chrome | `environment_gap` | 建议替代方案 / 要求装依赖 / 改 SOP 用 GUI |
| 页面结构与 SOP 描述不符 | `reality_mismatch` | 更新 SOP 描述 + **附截图/录屏给中台看** |
| 验收标准自相矛盾 | `spec_conflict` | 修订 SOP |
| 试了 15 轮都不行 | `capability_exceeded` | 转人工 / 换台机器 |

**「附录屏给中台看」就是 Qwen 视频理解的落点**（[05 §4](./05-qwen-multimodal.md)）——现在它更有价值了：执行器 Agent 卡住时，录屏是最高效的表达。

| 是否接受任意代码执行 | `codeExecution`：`off` / `sandbox` / `host` | `sandbox` | 按合规等级选 |
| 沙箱强度 | `sandboxBackend`：`none` / `process` / `container` / `vm` | `process` | 按运维能力选 |
| 能否操作已登录软件 | `hostAccess`：`none` / `app-scoped` / `session` | `none` | 按最小权限原则选 |
| 直接执行任务方式 | `taskExecution`：`deploy-only` / `isolated-runner` | `deploy-only` | 按是否需自验证选 |

**关键设计**（[09 §1](./09-permission-profiles.md)）：
- **默认最保守**：开箱即用档位为「什么都不能做」，高级能力需显式开启
- **代价明示**：每档写清「会失去什么保护」，供企业 IT 判断
- **中台可管控**：`最终档位 = min(客户端配置, 中台上限)`——IT 能保证员工改配置也不突破公司策略
- **不提供自伤选项**：`shared-runner`（复用 `/execute`，会破坏 manifest 劫持防护）**故意不做成配置项**
