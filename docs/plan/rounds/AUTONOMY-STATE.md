## 本轮落地：ADR-039 —— 一个有力的**否定结论**（`b3e11966`，W3）
**问题**：`execute` 503 行的剩余主体是「事务耦合段」，要再瘦身必须先改事务设计（backlog `execute-further-slimming = needs-adr`）。

**结论**：**`execute` 里 0 个显式事务** —— 全区间无 `transaction` / `manager.` / `queryRunner`。本仓执行器核心是「**无事务 + 单语句 CAS**」：
- `approvals.consume`（`agent-approvals.service.ts:788`）是一次**带谓词 update**、只看 `affected` ⇒ **单语句 CAS 即原子**，不需要事务；
- 台账写入各自独立提交（`persist` 闭包 `:321`，失败退回插入）；
- 正确性靠**三条不变量**：① 严格顺序（闸门 `:485` → 领取 CAS `:601` → 副作用 → 台账）② 单判据 `ledgerRowExists:314` ③ 可结清（条件写幂等）。

**四案**：**A** 分区注释（0 收益 0 风险）；**B** 抽「审批查+三分支」纯函数（不拆事务，但 CAS 的 `affected` 就是决策结果 ⇒ **只能抽三个拒绝分支**，省 25–35 行）；**C** 拆两事务+幂等键（**凭空引入**事务 ⇒ CAS 失效窗口 / 审批单永久作废 / 漏结清，**三类失败全静默**）；**D** 审批链搬协作者（省 ~150 行，**被 R99 硬裁决禁止**）。
**推荐 A + 建议关闭 `execute-further-slimming`**（将来确需再瘦只做 B，**不许**碰 C/D）。

**方法论（写进 ADR §1.2）**：「**优化事务边界**」这个提法本身是误导 —— 真正的约束是**因果顺序**与**单判据**；一旦有人以「事务边界」为名去拆，最容易的后果是把「**一条语句成功即事实**」变成「**一段时间内的状态**」，而 R60/R61 的全部论证都建立在「事实」而非「时间窗」上。C 案的风险特征是：**代码看起来更干净、测试更绿，而故障几周后以审计面不一致的形式出现**。
