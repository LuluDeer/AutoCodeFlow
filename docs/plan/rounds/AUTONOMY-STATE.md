## 教训（300–302）
- **300「判据在读注释还是在读实现」决定它是在保护还是在制造噪音** —— 裸正则扫全文把「**文档里提到这个开关**」当成「**实现了这个开关**」；本仓头注写「用法：… `--selftest`」是**常态** ⇒ 判据必须先做「**只抹注释、保留字面量**」的预处理（`stripCommentsKeepStrings`），**不要信任「正则匹配到了就是实现」**。① **注释专用预处理件不能借用「连字符串一起抹」的那版**（会把实现一起抹掉）；② **看误报方向** —— 多报时「把注释改掉让它闭嘴」是**最坏**的修法（判据在读注释，于是改注释就等于改好了「检查」），正确修法是**让判据改读实现**。
- **301「剥注释」不能把实现也剥掉** —— 修「误判注释」最容易过头的是把**字符串字面量**一起抹掉（那样真开关也会消失，判据从「多报」翻成「漏报」，**且看起来像是修好了**）⇒ selftest 用例必须**双向**（纯注释 ⇒ 不算 / 注释 + 真实开关并存 ⇒ 仍算）。① **单向下界会掩盖「修过头」**（只测「纯注释不算」时，把实现也抹掉的方案一样通过）；② **修「误判」类缺陷，用例必须成对**（误判方向 + 正例方向），否则修法越狠得分越高；③ **「剥什么」要写进函数头注** —— 两个 `stripComments*` 名字几乎一样、用途相反，不写清就会有人拿错。
- **302「判据被自己的文档误伤」是一个递归陷阱** —— 触发器是「**我在注释里写了 `--selftest` 这个词**」：**给判据补口径的动作本身可能把判据弄乱**。与 **293**「注释也会与实现相反」同族但**方向相反**（293 是「注释与实现相反」，本轮是「**注释被当成了实现**」）⇒ ① **给判据补口径/补注释时，必须设想「文档或注释里出现这个词」的后果**；② **判据的文档与被判的对象要隔离**（本轮的反讽：那句话本来在**说明它没有这个开关**，结果**那句话本身**被当成了有这个开关的证据）；③ **同一份源码里「说明」与「实现」共用一套字符时，先分层再匹配**（注释层 / 字面量层 / 代码层）—— 与 293 合起来是同一结论的两个方向：**注释既不能信（可能与实现相反），也不能算（可能被当成实现）**。
