- **R233（`885f6510`）治「跑测试把整机拖死」**（用户报告）。
  **证据**（`journalctl -k`）：`node-V8Worker invoked oom-killer … global_oom`，杀掉**微信/Firefox/awesun**；
  `pgscan_direct` 是 `pgscan_kswapd` 的 **15 倍** ⇒ 进程同步等内核回捞页 = **整机冻结+时钟停走**。
  **三层根因**：① jest 无 `maxWorkers` ⇒ **15 worker**（16 核）② 每 worker 堆 2144MB ⇒ 峰值 **32GB** vs 物理 13GB
  ③ direct reclaim → 冻结 → OOM killer。**swap 不是元凶**（NVMe 上），但 **4GB 偏小**（**该扩不该缩**）。
  **修法**：`maxWorkers` 15→**4** · `workerIdleMemoryLimit` **1GB** · 堆上限 2144→**4096MB**。
  **验证**：`test:api` **连跑两次**均 **492 套 8283 例全绿**；峰值 **8811MB**、未 OOM。

  DNS 级 SSRF 闸却在**路由入口**`:886` ⇒ **DNS 先跑**，解析到受限段时文案
  `…受限网络地址：${gitRepo}` **回显含 `user:token` 的完整 URL**（**accept 期就泄**）。
  **python 顺序是对的 ⇒ node 独有**。修法：userinfo 前置（纯字符串），文案不含原 URL。
  **验证**：失败数 **29 → 28**、零回归。

## 教训（440–441，接 439）
- **440「用户描述的症状比我的第一层归因更值钱」** —— 我最初只见 `exit 134 / Aborted`，归因为「V8 堆耗尽」并准备只调堆上限。用户补「整机卡住、时钟停走、很多程序被杀」⇒ 那**不可能是 V8 abort 的表现** ⇒ 才去查 `journalctl`，找到全局 OOM 与 direct reclaim。**没有这句补充，我会交一个只治标、峰值反而更高的修复**（15×4GB=60GB）。⇒ 「**整机级**现象」是区分进程内/系统级问题的第一手线索。
