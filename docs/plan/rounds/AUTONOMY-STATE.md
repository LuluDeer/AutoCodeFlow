- **缺陷**：本仓三条入队路径 jobId 不同（首跑 `session.id` · 人工/审批恢复 `${id}:resume:${ts}` ·
  LLM 自动续跑 `auto-resume-<id>`）。一条「**审批通过、正在正常等排队**」的会话，`getJob(session.id)`
  查不到 ⇒ **判成积压** ⇒ 运营按提示「重新入队」⇒ **同一会话跑两遍（双份副作用）**。

- **判据修正**：`findSessionJob` **有限枚举**三个形态（首跑 → `resume-<id>` → `auto-resume-<id>`），
  命中即返回。**刻意不扫全队列**（O(n) + 有上限 ⇒ 会漏）。**首跑仍零额外往返**。
- **配套**：resume 的 jobId 改为可枚举 `resume-<id>`（新增 `manualResumeJobId`）。
  **不是 `${id}:resume`** —— 实测 BullMQ 拒 2 段冒号 id。**去重语义已变**（重复 resume ⇒ 幂等 no-op），
  已登记并用例钉住。
- **「自动补 enqueue」立项结论**：**先修误报，再谈自动补** —— 在误报存在时做自动补，
  会把观测缺陷放大成**真副作用**。前置已清，下一步可安全立项。

## 教训（420–421，接 419）
- **420「『将来可能坏』和『现在就是坏的』之间只差一次代码对照」** —— R202 把 `jobId === session.id` 的风险写成「若**将来**改成随机 jobId」，读起来像未雨绸缪，实际本仓**当时就有三条路径**不符。⇒ 写「已知边界」时，凡涉及外部约定，**必须列出当前所有实现该约定的地方**。
