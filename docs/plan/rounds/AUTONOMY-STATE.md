## 教训（258–261）
- **258 数据源有多条写入路径时，每条都要接上**：R142 只接了单端快照、漏了全量体检 ⇒ **一次体检就把数据擦掉**。上一轮已写成 256，但**「写下」不等于「还清」** ⇒ 判据：**「扩一个数据源」必须先列出所有写入端，再逐个点名检查**；只改读取端 = 只修了一半（且是最难被发现的那一半，日常没人跑全量）；
- **259 新增「只跑一部分」的模式时，语义要写死互斥与复用**：`--only` 与 `--skip-heavy` **互斥 ⇒ exit 2**（**不定义「谁会赢」的暗规则**）；**未命中的 step 原样沿用**、不丢数据（`--only` 的用途是**真验证某一端**，不是重建基线）；**0 命中必须 exit 1 而不是静默**（静默跑全量 = 用户以为只跑了一步，实际跑了半小时）；
- **260 同一能力的多个客户端要补齐到同一语义**：A6b 走 Web → CLI → MCP 逐个补，每端用**同一条判据**收口 ——「**未传时请求体逐字节一致**」。它比「功能可用」强得多：同时钉住**向后兼容**与**缺省语义**（发 `false` 会让「未传」与「传 false」不再等价，而后端本是同一个默认）⇒ 补第二/第三个客户端时**先找到第一个客户端的判据并照抄**；
- **261 小分母上的容差会退化成 ±0**：16 个测试文件时 5% 容差 = **不许变** ⇒ 新增 1 个文件就要同步文档。守卫红**不是「太严」**，是提醒**数字该回写了**；「容差是百分比」这句话**在大分母上成立、在小分母上不成立**。
