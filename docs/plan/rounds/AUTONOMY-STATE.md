## 教训（291–293）
- **291「可观测性」要落到「失败时能直接看到原因」** —— 本轮之前链红只给段号/退出码，真原因在**几十屏之外**；**R21 解决「红在哪段」、R153 解决「这段为什么红」**。① 判「可观测性做完了没有」看的是「**失败时人要移动多少次视线**」，不是「有没有日志」；② **诊断信息要与判定结论同址**（放进失败报文）—— 人的默认行为**不是去找，而是重跑一遍**，偶发缺陷因此永远归不了因；③ **加信息时必须显式核「判定有没有跟着变」**（fail-fast / 退出码原样传播 / 逐段行格式，三条逐条核过）。
- **292 `stdio: "inherit"` 与「可诊断」是互斥的** —— inherit 实时性最好，但**父进程拿不到内容** ⇒ 只能报「谁失败」、报不了「为什么」。① 要**实时性 + 可回放**，只能**双向 pipe + 实时透传 + 环形缓冲**，**不是二选一**；② 缓冲要**环形 + 有界**（最近 20 行），全量留存会把父进程变成第二个日志仓库（分钟级段会撑爆内存与报文）；③ **信号与退出码要分开记** —— `code=null && signal!=null` 与「自己 exit 1」是两种故障，旧报文把两者都写成 `exit 1`（比缺 stderr 更误导：让人查代码而不是查 OOM/超时）。
- **293 注释也会与实现相反，而且比代码更难被发现** —— `ci.yml` 写「只跑主跑」而 R145 已含自检，**没有任何判据会因注释过时而变红**。① **改了脚本语义就要 grep 一遍注释里的同一说法**；② **「注释说没做」比「注释没说」更危险**（让人重复做一遍，或把已接上的东西摘掉）；③ 注释的判据形态只能是**与实现同源**（引**符号**不引行号、引**脚本行**不引转述）—— 与 250「过期事实先核时间戳再改文档」同族。
