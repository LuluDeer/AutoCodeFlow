## 本轮落地（R210 · 1 项 · 已复核）

**★「停摆」判据的误报窗口 —— 误报确实存在，但成因不是文档写的那个；真成因是一条能触发的假告警。**
- **★ 真机推翻文档前提**：文档写「事件循环阻塞 ⇒ 心跳过期 ⇒ `workers` 归 0 ⇒ 误报」。**实测不成立** ——
  `getWorkers()` **不读心跳注册表**，而是数 Redis **`CLIENT LIST`** 的连接名（`queue-getters.js:454`）。
  实测：**同步忙等 8 秒期间 `workers` 仍是 1**；只有 `worker.close()`（连接真断）才降 0。
  ⇒ 「阻塞导致误报」这一类**根本不会发生**，`workers===0` 是**结构性事实**。
- **★ 找到并修掉真实误报路径**：`read(() => getWorkersCount(), 0)` —— **读失败回落成 0** ⇒ 若
  `active===0` 且有活排队就判 `stalled` ⇒ **一次 Redis 抖动 = 一条假告警**。这是「没读到渲染成
  **有问题**」——本仓修过 10+ 例的反向镜像，代价同样是运营不再信徽标。
  **修法**：`paused`（独立强证据）单独成立；`workers` 那一路要求**它自己读到了**。
  **刻意不写「degraded 就一律不报」**（那会吞掉真停摆，与另四徽标同款取舍）。
- **顺带修一处错误归因**：`reason` 原复用 `queueStallReason()`（内部再判一次、且不区分真 0 与
  读失败）⇒ 「paused 成立 + workers 读失败」时错报 `no-worker`（让人去查进程）。改为按已确认证据归因。

## 教训（410–411，接 409）
- **410「误报的成因也要验证，不能继承前任的猜测」** —— R204/R205 把「阻塞⇒心跳过期⇒误报」当已知事实并**据此设计**，两轮没人验过；实测连**实现机制**都描述错了（不是注册表，是 `CLIENT LIST`）。⇒ 「已知误报」必须能指到实现**哪一行**；指不到就当**未验证假设**，别让它变成设计前提。
- **411「『读不到』在告警方向上的镜像」** —— 本仓修过 10+ 例「读失败渲染成没有」，但**反向**（渲染成**有问题**）同样有害：制造假警、消耗信任。⇒ 凡是「某量决定要不要报警」，回落值必须**与报警方向对齐**（单独建模「未知」，或让回落值**不触发**报警）。

1. **`workers === 0` 的「未知」语义**（M）—— 本轮只让「读失败」**不触发**报警，但契约上
   `workers` 仍是 `number`（「0」与「不知道」在响应里**同形**）。要与 R205 已发布契约兼容地
   加一个「未知」表达（例如 `workersKnown: boolean`），改动会波及前端徽标与既有 spec ⇒ **独立立项**。
2. **`degraded` 的真机触发**（S）—— 本轮只由单测覆盖。可在**独立 Redis 命名空间**上做：起一份 admin-api 指向临时 Redis，跑中 `SHUTDOWN NOSAVE` / 断连 ⇒ 断言端点返回 `degraded:true` 且 `idleStuck:false`（**不影响**真实 Redis）。
