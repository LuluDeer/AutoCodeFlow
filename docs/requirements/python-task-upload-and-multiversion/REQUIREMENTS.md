> **特性名（feature_name）**：`python_task_multiversion`
> **文档类型**：需求规格说明书（Requirements Specification）
> **需求格式**：EARS（Easy Approach to Requirements Syntax）
> **状态**：待负责人确认（DRAFT v0.3）

## 1. 需求背景与业务目标

### 1.1 背景

**[v0.3 修订]** 负责人手头存在 **Python 3.7 实现的历史存量项目**（其依赖声明 `python_requires` 上限为 3.7，宿主解释器 3.12 无法解析安装）——本项目接入平台的驱动案例。经范围澄清，能力目标由"支持 3.7 存量项目"**泛化为"任务可指定任意受支持的 Python 版本运行"**：任何版本特征与宿主解释器不匹配的项目（3.7 存量遗留、3.9 LTS 遗留、3.13 新特性项目等）都可按其声明的版本选取对应解释器运行，不限于 3.7。

1. 通过"应用管理"页面上传 zip 包（用户原以为该通道即"上传整个项目"），作为任务代码接入；
2. 任务执行时按**任务声明的 Python 版本**（任意受支持版本，如 3.7 / 3.9 / 3.12 / 3.13）选择对应解释器创建虚拟环境并运行，而不是被强制绑定到执行器宿主解释器（当前为 Python 3.12）。

### 1.2 业务目标

1. **G1**：新增"整包上传"作为第四种任务代码接入渠道，打通 `zip 上传 → 任务引用 → 执行器下载/解压/建环境/运行` 的完整链路。
2. **G2**：**[v0.3 修订]** 任务可声明其要求的 **任意受支持 Python 版本**（uv 支持区间内），系统能按声明**获取对应版本解释器并创建 venv 与运行**；3.7 存量项目及任意版本特征项目均可运行。**3.7 为本能力的代表性子集（示例/验收用例之一），非唯一目标。** 解释器获取方式为：执行器内置 uv 按需动态下载目标版本 CPython 进入本地缓存池并复用，而非依赖镜像预装或部署方手工提供。
3. **G3**：在达成 G1/G2 的同时，保证既有 git / glue / PyPI 三种接入渠道的既有行为不回退（向后兼容）。

## 2. 术语与缩写

| 术语 | 定义 |
|---|---|
| **任务代码接入渠道** | 任务获取代码/运行产物的方式。现状共三种：gitRepo（git clone）、glue（在线内联脚本）、PyPI wheel（私有私服包引用）。本需求引入第四种：整包上传（zip）。 |
| **宿主解释器** | 执行器进程运行时所在的操作系统解释器（executor-python 镜像为 python:3.12-slim）。 |
| **任务声明的 Python 版本** | **[v0.3 修订]** 任务配置中声明的期望 Python 版本（取值为主.次版本的 `X.Y`，可为**任意受支持版本**，如 3.7 / 3.9 / 3.12 / 3.13），用于在解释器获取与匹配时选择 venv 创建所用解释器。 |
| **受支持版本区间** | **[v0.3 修订·新增]** uv 官方支持政策确定的解释器版本范围：Tier 1 = 3.10~3.14（完全支持）；Tier 2 = 3.6/3.7/3.8/3.9（预期可用）；uv 不支持 <3.6。任务可声明的版本即区间内任意主.次版本（可靠性分层见 §3 事实 9 与 §9 支持矩阵，最终以 D10 实测为准）。 |
| **解释器缓存池（interpreter cache）** | 执行器本地存放已下载 CPython 解释器的目录（`UV_PYTHON_INSTALL_DIR` 定位）。解释器由 `uv python install <version>` 按需动态下载（python-build-standalone 构建产物）后落入该池；同一宿主上多个任务 venv 复用池内同一解释器层，避免重复下载。 |
| **解释器清单（interpreter inventory）** | 执行器本地解释器缓存池中已下载且可用解释器版本集合（来源：`uv python list --only-installed`），执行器启动/心跳时上报 admin。 |
| **venv（虚拟环境）** | 每个任务在 `work_dir/.venvs/<key>` 下由 uv 创建的独立 Python 虚拟环境，任务依赖安装于其内。 |
| **应用管理上传（zip）** | 现有 `POST /api/applications/upload`（≤200MB）通道，存储 zip 并产成 `packageUrl`；当前仅 executor-node 的 `/api/deploy` 应用部署通道消费。 |
| **executorId pinning** | 任务将 `executorId` 固定到指定执行器的机制，可绕过 group/tags/runtime 过滤。 |

## 3. 现状分析与约束前提（已核实）

> 以下为已核实的现状事实，构成本需求的约束基础，不随本需求改变；v0.2/v0.3 新增事实标注对应修订标记。

1. executor-python 官方镜像为 `python:3.12-slim`，以非 root `appuser` 运行；venv 由 `uv venv` 创建（不指定解释器，即取 PATH 中默认 Python 3.12），依赖经 `uv pip install --index-url <私有 PyPI>` 安装。
2. 无 requirements 的 python 任务直接以 `sys.executable`（执行器自身解释器，3.12）运行。
3. `任务表(tasks)` 已有 `runtime` / `runtimeVersion`（**仅元数据，执行器不消费**）/ `entrypoint` / `requirements`(jsonb) / `gitRepo` / `executorId` 等字段；`runtimeVersion` 当前不参与任何执行决策。
4. `POST /api/applications/upload`（≤200MB）：扩展名白名单 + ZIP 魔数校验 + clamd 病毒扫描后落盘 `uploads/packages/`，生成 `packageUrl`，对 application 实体做 upsert。
5. `executor-node` 的 `/api/deploy`（应用部署通道）是当前唯一消费 `packageUrl` 的通道，与任务调度通道无关。
6. "执行器包 executor-packages"（≤500MB）是执行器程序自身的安装/升级包，**不是**任务代码渠道，本需求不涉及。
7. 执行器注册表 `executors` 表已有 `type` / `capabilities` / `groupName` / `tags`，调度按 group/tags/runtime 过滤 → 亲和/反亲和 → loadScore 择优。
8. executor-python 自身依赖（fastapi 0.136.3、pydantic v2、uv 0.8.17 等）要求 Python ≥3.8，**执行器本体无法降级运行在旧版本（<3.8）**——多版本能力通过"**uv 按需动态下载解释器进入本地缓存池，按任务声明选择**"实现，而非"执行器本体跑在目标旧版本"。**[v0.2 修订]**
9. **[v0.3 修订]** uv 官方 Python 版本支持政策（docs.astral.sh/uv/reference/policies/python/，2026-03-19 版）：Python **3.10~3.14 为 Tier 1**（完全支持、官方测试覆盖）；Python **3.6 / 3.7 / 3.8 / 3.9 为 Tier 2**（"expected to work"，uv 有对应测试）；uv 明确**不支持 <3.6**。即**受支持区间为 3.6~3.14（含上下界）**，其中 3.6 位于 Tier 2 下界、属政策边缘。任务可声明的版本为区间内任意 `X.Y`；最终可用区间以 D10 实测 uv 0.8.17 可下载列表为准。
10. uv 解释器获取命令语义（0.8.x 已验证）：
    - `uv python install <version>`：显式下载并安装指定版本 CPython（python-build-standalone 构建产物），结果落入本地解释器缓存池；
    - `uv venv --python <version>`：以其指定版本解释器创建 venv；系统在缓存池缺失时默认自动下载后创建（等价于先 `install` 再 `venv`）；
    - `uv python list --only-installed`：列出缓存池中已安装的解释器版本；
    - `uv python list --all-versions`：列出当前 uv 版本**可下载**的全部解释器版本（用于 D10 完整区间实测）；
    - 受控配置入口：`UV_PYTHON_INSTALL_DIR`（缓存目录定位）、`UV_PYTHON_INSTALL_MIRROR`（下载镜像）。
11. **[v0.3 修订]** **风险点（必须验收验证）**：uv 每个发布版本的"可下载 Python 版本列表"是**冻结**的（"available Python versions are frozen for each uv release"）。本平台锁定 uv 0.8.17（见事实 13），须在验收中实测 `uv python list --all-versions` 确定 **0.8.17 可下载版本的完整区间（含上下界）**，据此明示支持矩阵。已知边界事实：python-build-standalone 对 3.7 的构建止于 **3.7.9**（Tier 2 下界附近）。若实测区间与本文支持矩阵（3.6~3.14）不一致，须升级/调整 uv 版本或切换自定义镜像源，该验证作为阻塞性前置验收项（见 D10）。
12. **[v0.3 修订]** 解释器下载默认源为 **Astral CDN / GitHub Releases**（python-build-standalone 产物），**在线动态下载为默认主路径（所有部署必有）**。私有化/离线场景为**可选部署模式**：部署方可在需要时启用 `UV_PYTHON_INSTALL_MIRROR` 内网镜像、或部署期离线预填解释器缓存卷（将已下载的解释器预先导入 `UV_PYTHON_INSTALL_DIR` 挂载卷）；两者为可选项而非全局硬约束（见 D9、NFR-14）。
13. 平台执行器已有 uv 前置依赖（即"客户端内置 uv"在代码库中已成立）：`apps/executor-python/requirements.txt` 固定 `uv==0.8.17`；`routers/execute.py` 以 `UV_BIN = shutil.which('uv') or 'uv'` 定位二元、venv 由 `uv venv --no-project` 创建。新增工作集中在"版本感知的 venv 创建 + 解释器按需下载调度 + 缓存池管理"，不引入新的运行时前置。

## 4. 功能需求（EARS）

> 需求编号约定：`FR-<序号>`（功能需求）。所有"系统"指 AutoCodeFlow 整体（admin-api + admin-web + 相关执行器）。每条需求附**验收要点（AC-<同序号>）**。修订处标注 **[v0.3 修订]**。

### 4.1 整包上传：作为任务代码接入渠道

**FR-01（Ubiquitous）**：系统须把"应用管理"页面上传 zip（`POST /applications/upload`）所管理的应用，纳入 Python 任务可选代码来源——即上传 zip 不只是服务于 executor-node 的应用部署，还可被 Python 任务引用为任务代码。
- AC-01a：用户在应用管理页面上传 zip 成功后，可在 Python 任务配置中引用该应用作为代码来源（如通过 `applicationId`）。
- AC-01b：已有 executor-node `/api/deploy` 应用部署语义不被破坏（见 NFR-06）。

**FR-02（When）**：当 Python 任务引用指定 zip 包且任务触发派发时，系统须将该包的下载与解压结果置于任务工作目录，作为任务代码，随后按任务配置安装依赖并运行入口文件。
- AC-02a：任务运行后，工作目录中存在 zip 解压出的项目文件。
- AC-02b：依赖安装与入口运行行为与 gitRepo 渠道一致（复用 venv + entrypoint 语义）。

**FR-03（When）**：当执行器下载并解压任务 zip 包时，系统须防护 zip 解压路径穿越（zip-slip，如 `../` 或绝对路径条目），拒绝任何解压结果逃逸出任务工作目录的包。
- AC-03a：构造包含 `../evil` 或绝对路径条目的恶意 zip 上传时，任务不运行，返回明确错误，且解压未产生工作目录之外的文件。
- AC-03b：该防护对 4.1 与既有 executor-node `/api/deploy` 两处解压点同时生效（executor-node 侧已有同类防护则可复用）。

**FR-04（Each）**：每个上传的 zip 包，系统须支持任务以两种依赖来源组合安装：包内 `requirements.txt` 与任务级 `requirements` 字段；两种来源合并去重后执行安装，且任务级 `requirements` 优先级更高（可覆盖包的版本约束）。
- AC-04a：包内含 `requirements.txt`、任务 `requirements` 为空 → 按包内清单安装。
- AC-04b：任务 `requirements` 非空 → 安装包内清单 ∪ 任务清单的并集合并结果（具体合并规则见 D4，已按建议落定默认值）。
- AC-04c：包内 `requirements.txt` 不存在且任务 `requirements` 为空 → 任务不创建 venv，直接以所选解释器运行入口文件（与现状无依赖任务一致）。

**FR-05（Each）**：每个被 Python 任务引用的 zip 包，在上传时须通过既有安全校验链：扩展名白名单、ZIP 魔数、clamd 病毒扫描、≤200MB 大小限制（复用 `POST /applications/upload` 现有校验，不新增第二套上传入口）。
- AC-05a：超限/非 zip/含毒上传被拒绝，错误提示明确。
- AC-05b：本需求不新增与既有上传接口重复的旁路上传通道。

### 4.2 任务级 Python 版本声明与匹配语义

**FR-06（When）**：当用户创建或编辑 Python 任务时，系统须允许其声明任务要求的 Python 版本（取值可为**任意受支持版本**，如 `3.7`、`3.9`、`3.12`、`3.13`，语义为"解释器主.次版本"）。
- AC-06a：任务表单/API 出现 Python 版本声明字段（复用或扩展 `runtimeVersion`，见 D3）。
- AC-06b：**[v0.3 修订]** 版本值非法（非 `X.Y` 格式、超出受支持版本区间 3.6~3.14）时拒绝保存并提示。支持区间以 uv 支持政策为准（见事实 9），最终以 D10 实测为准。
- AC-06c：任务保存时系统仅校验版本格式与支持范围，**不预检**执行器是否已缓存该版本——解释器"先下载后有"，首跑时的获取失败在运行时体现（见 FR-07/FR-08）。

**FR-07（Anytime）**：**[v0.3 修订]** 任何时候系统为 Python 任务创建 venv 时，须使用**任务声明的 Python 版本对应解释器**（任意受支持版本，Tier 1 = 3.10~3.14 / Tier 2 = 3.6~3.9，见事实 9）创建 venv；venv 安装依赖与运行入口文件均使用该解释器。若该解释器尚未进入执行器本地缓存池，**首次执行须触发 `uv python install <version>` 按需下载，下载耗时计入任务执行耗时并纳入任务超时预算**（见 NFR-13，单次下载独立预算默认 300s 见 D11）；下载完成后以其创建 venv。
- AC-07a：声明 3.7 的任务运行时，`venv` 内解释器版本为 3.7.x（存量驱动示例；可由 `script --version`/`python_requires` 校验）。
- AC-07b：任务 `requirements` 中声明 `python_requires <3.8` 的依赖在 3.7 venv 中安装成功、在 3.12 venv 中本会失败——本需求后该任务成功运行（3.7 语义对任意受支持版本均成立）。
- AC-07c：**[v0.3 修订]** 在"仅内置 uv、缓存池为空、无任何预装 3.13"的执行器上首次运行声明 3.13 的任务 → 自动下载 3.13 解释器并成功创建 venv、运行成功；执行日志可见下载动作，任务执行总时长包含下载耗时。该语义对区间内任意受支持版本（如 3.7/3.9/3.12/3.13）均成立。

**FR-08（When）**：**[v0.3 修订]** 当任务声明的 Python 版本（任意受支持版本）在其候选执行器上**无法获取**时——本地缓存池缺失且按需下载失败或下载源不可达——该执行器不得被选为任务的执行目标；若所有候选执行器都无法获取，系统须将任务派发改判为失败，返回不含歧义的错误信息（含任务声明的版本、各候选执行器的缓存/可获取版本），**失败分因记为 `interpreter_unavailable`**。
- AC-08a：仅一台缓存池中仅 3.12、且 3.9 下载源不可达的执行器在线，调度声明 3.9 的任务 → 任务失败，失败分因 `interpreter_unavailable`，错误信息明确"3.9 不可获取（缓存缺失 + 下载不可达）"。
- AC-08b：通过 `executorId` pinning 强制指定不满足版本声明的执行器时，行为须在创建/运行阶段至少一处明确报错（建议运行前报错，见 D2）。

**FR-09（Anytime）**：任何时候系统在调度派发 Python 任务时，须将任务声明的 Python 版本作为与 `executorGroup` / `executorTags` 同级的硬性过滤条件，与现有 group/tags/runtime 过滤、亲和/反亲和共同生效；过滤依据为各执行器上报的解释器清单（缓存池已装版本，见 FR-13）**及**其能否按需获取声明版本（下载可用性）。
- AC-09a：`executorTags` 与版本声明同时不满足的执行器被排除；仅版本可获取的执行器被选中。
- AC-09b：过滤失败时给出的候选执行器快照中，须标出每个执行器的已缓存解释器版本，便于定位。

**FR-10（Where）**：对于不声明 Python 版本的任务（`runtimeVersion` 为空），系统须保持既有行为不变——仍以执行器宿主默认解释器创建 venv/运行（现状语义：Python 3.12），**不触发任何解释器下载**。
- AC-10a：存量任务在新版本系统上运行结果与旧版一致（解释器版本选择、venv 行为均不改变）。

**FR-11（Where）**：当任务为 glue（内联脚本）或无依赖类型时，系统须忽略任务声明的 Python 版本说明中的 venv 创建步骤（glue 无 venv）；但若用户对 glue 任务声明版本，系统须以该版本对应解释器执行脚本（同样"先下载后有"，见 FR-07）。
- AC-11a：对 glue 任务声明 3.9 → 以 3.9 解释器执行内联脚本；不声明 → 现状（宿主解释器）。
- AC-11b：glue 任务始终不创建 venv、不安装 requirements（现状不回退）。

**FR-12（Each）**：**[v0.3 修订]** 每个因 Python 版本**无法获取**（`interpreter_unavailable`：缓存缺失且按需下载失败/下载源不可达）而未运行的执行记录，须在任务执行记录的失败原因中持久化：声明的版本、尝试下载的版本与结果（含失败原因）、检查到的候选执行器及其缓存/可获取解释器版本，并存留至相关日志与执行详情。
- AC-12a：执行详情页可见"声明版本 3.13；候选执行器: exec-a[缓存 3.12], exec-b[3.8.3；3.13 下载失败：无法访问下载源]"类事实信息。

### 4.3 执行器解释器动态下载与缓存池

**[v0.2 修订]** 本节整体从"镜像预装多解释器 + 启动扫描"重构为"**uv 按需动态下载 + `UV_PYTHON_INSTALL_DIR` 本地缓存池复用**"。**[v0.3 修订]** 下载目标版本不再限于 3.7，可为受支持区间内任意版本。

**FR-13（Ubiquitous）**：**[v0.3 修订]** 系统须支持执行器通过内置 uv **按需动态下载**多个 Python 版本解释器（受支持区间内任意版本）进入本地解释器缓存池（`UV_PYTHON_INSTALL_DIR`，多个任务 venv 复用同一解释器层），且执行器把"缓存池中已安装解释器版本清单"作为自身能力的一部分纳入注册表与心跳上报。
- AC-13a：`executors` 表 / 注册 payload 中出现可查询的解释器清单（如新增 `interpreters` 数组或复用 `capabilities`——见 D5）。
- AC-13b：执行器至少支持一个版本（存量仅宿主 3.12 的执行器注册清单为 `["3.12"]`，不强制预下载；下载 3.9 后清单变为 `["3.9", "3.12"]`）。

**FR-14（Each）**：每个执行器进程在启动时，须通过 `uv python list --only-installed` 发现本地缓存池中已安装的解释器版本清单，并随注册/心跳上报；运行中不得因单条探测子命令失败而整体启动失败。
- AC-14a：缓存池含 3.7 + 3.12 的宿主上报清单 `["3.7", "3.12"]`（示例）。
- AC-14b：某解释器路径损坏/不可执行 → 只从清单剔除该版本，执行器仍正常注册并上报其余版本。

**FR-15（When）**：当执行器为任务创建 venv 时，须以显式参数指定任务声明版本的解释器（`uv venv --python <已下载解释器版本或路径> --no-project <venv目录>`），不得依赖 PATH 默认解释器；若缓存池中该版本缺失，须先按 FR-07 完成下载再创建。
- AC-15a：venv 内解释器版本与任务声明一致（代码审查 + 运行验证双重确认）。
- AC-15b：宿主 PATH 默认解释器与任务声明不同时，venv 仍使用任务声明版本（即不受 PATH 影响）。

**FR-16（Each）**：每个使用指定版本解释器创建的任务 venv，其目录标识须纳入解释器版本维度的签名（`taskId-<版本>`），避免不同版本任务复用同一 venv 目录导致交叉污染。
- AC-16a：同一任务先后在其声明版本变更（如 3.7 → 3.9）后，再次运行时使用独立 venv；旧 venv 留在磁盘等待既有 TTL 清扫，不混用。
- AC-16b：同版本复用既有 venv（性能目标，见 NFR-11）。

### 4.4 与现有三渠道的关系

**FR-17（Anytime）**：任何时候，现有三种任务代码接入渠道（gitRepo、glue、PyPI wheel）都须保持其既有行为，不因新增整包上传渠道而改变，且新增渠道不改变任意既有任务的运行结果。
- AC-17a：既有 git / glue / PyPI 渠道测试用例全部通过（回归）。
- AC-17b：三条渠道与新增 zip 渠道在任务配置上可区分（不产生语义歧义的字段重用）。

**FR-18（Each）**：每个任务在代码来源上须满足"恰好一种"来源通道——整包上传 vs gitRepo vs glue 不允许多选叠加。
- AC-18a：选择了 zip 包引用的任务不可同时填写 gitRepo；反之亦然。配置互斥校验在保存时拦截并提示（glue 同理）。
- AC-18b：互斥规则不拒绝 PyPI wheel 渠道（它通过 requirements 引用，可与 gitRepo/zip 代码来源自然并存）——即所有"代码来源型"渠道互斥，依赖型渠道（requirements/PyPI）可叠加。

**FR-19（When）**：当整包上传的 zip 包内容明确是 Python 项目（包内存在 `requirements.txt` 或 Python 源码入口）时，系统须在任务侧（或部署侧）给出与运行时一致的 Python 运行语义的提示/校验一致性——不得出现前端判定为 Python 项目而后端按非 Python 处理的不一致。
- AC-19a：上传 zip 的应用，其 `runtime` 字段判定与任务实际执行 runtime 一致时任务可运行，不一致时给出明确配置错误。

## 5. 非功能需求（NFR）

### 5.1 安全

**NFR-01**：任务代码解压与执行在非特权上下文（现状：`appuser`）中进行，不得以 root 运行任务代码；本特性不得提升任何权限面（Ubiquitous）。
- AC：上传包执行身份的 UID/权限与现状任务一致；无新增特权。

**NFR-02**：任一解释器加载路径仅限解释器缓存池（`UV_PYTHON_INSTALL_DIR`）内由 uv 安装/缓存的解释器（防止任务通过 `requirements`/环境干扰选择到任意可执行文件作为"解释器"）（Ubiquitous）。
- AC：解释器清单只来自缓存池白名单；不可由任务参数注入任意解释器路径。

**NFR-03**：任务声明的版本选择、解释器路径解析、venv 创建参数不得接受任务提供的可执行路径或 shell 拼接（防注入）（Ubiquitous）。
- AC：构造恶意 `entrypoint`/`requirements`/版本字符串的测试通过，无命令注入。

**NFR-04**：上传的 zip 包在任务侧落地前须经过与上传时相同强度的校验（校验信息可在 admin 侧随派发附带或执行器侧复检）（Each 上传 → 校验）。
- AC：绕过 admin 直接向执行器投递含毒/超限 zip 的用例被拒绝。

### 5.2 向后兼容

**NFR-05**：`runtimeVersion` 字段对既有数据保持可选；未设置该字段的存量任务、未按版本化 venv 改造前的逻辑均保持原行为（Ubiquitous）。
- AC：未设置 runtimeVersion 的存量任务在新版本下执行结果与旧版一致（前置覆盖 FR-10/AC-10a）。

**NFR-06**：`POST /applications/upload` 对 executor-node `/api/deploy` 应用部署通道的既有契约（上传、`packageUrl` 格式、部署语义）保持不变（Ubiquitous）。
- AC：executor-node 应用部署 e2e 用例全部通过；`packageUrl` URL 结构不变。

**NFR-07**：`registry-pypi` 私有源与 uv 索引配置不因本特性改变（Ubiquitous）。
- AC：依赖安装仍仅使用白名单私有源或显式允许源。

### 5.3 性能

**NFR-08**：解释器版本匹配与选择不得引入显著派发开销——匹配行为基于执行器已上报的缓存清单（内存查表），每任务 O(解释器清单长度) 以内（Ubiquitous）。
- AC：百万次匹配基准 ≤1ms/次（无网络/IO 参与）；派发链路新增时延 ≤5ms。

**NFR-09**：zip 下载 + 解压属于任务准备阶段，须纳入既有任务超时语义（任务超时覆盖环境准备阶段），不得出现准备阶段不受控挂起（Ubiquitous）。
- AC：下载/解压超时后任务进入失败态，错误信息含准备阶段超时定位。

**NFR-10**：解释器缓存池发现（`uv python list --only-installed`）不得使执行器冷启动时间显著劣化——清单探测并行执行，探测全量 ≤5s 上限（Ubiquitous）。
- AC：缓存池含 2 个解释器的宿主，执行器启动到注册上报时间增量 ≤5s（与基线对比）。

### 5.4 磁盘

**NFR-11**：每个任务的 venv + 包内代码解压总占用须受既有磁盘上限/清扫策略约束（TTL 清扫覆盖解压目录与 venv，**不含解释器缓存池层**——后者由 NFR-15 体积红线治理），本特性不得引入新的无主磁盘泄漏（Ubiquitous）。
- AC：任务结束/过期后其解压目录与 venv 被清扫；TTL 用例通过。

**NFR-12**：**[v0.3 修订]** 每个下载/缓存进池的一个解释器版本占用磁盘量须有上限红线（**默认值：单版本 ≤250MB**，python-build-standalone 基座，见 D12）；缓存池总占用默认 ≤4GB。部署文档/镜像说明给出缓存池总占用；超过红线时告警并回收最久未使用版本（见 NFR-15/D12）（Each 下载入池 → 记录）。
- AC：部署文档/镜像说明中给出解释器缓存池总占用；达到红色线触发告警与回收行为。

### 5.5 解释器下载与缓存 [v0.2 修订·新增小节]

**NFR-13**：**[v0.3 修订]** 解释器按需下载（首次执行触发的 `uv python install`）须纳入任务既有超时预算——下载耗时计入任务执行耗时、受同一任务超时约束；此外**单次解释器下载设独立超时预算，默认 300s（可配置，见 D11）**，两者取较小值生效；下载悬挂须中断并使任务失败（Each 下载 → 计时）。
- AC：在受限带宽/不可达环境下触发目标版本（如 3.13）下载的任务，超时预算内完成下载则运行成功、超时则失败且错误信息含"解释器下载超时"定位。

**NFR-14**：**[v0.3 修订·改写]** **在线动态下载为解释器获取的默认主路径，所有部署必须可用**（Ubiquitous，最高优先级）。私有化/离线部署为**可选部署模式**：部署方可选择启用 `UV_PYTHON_INSTALL_MIRROR` 内网镜像，或离线预填解释器缓存卷（解释器预先导入 `UV_PYTHON_INSTALL_DIR` 目录卷）；两通道作为**部署配置文档化**，不构成全局硬约束（在线主路径与可选模式关系见 D9）。
- AC-NFR14a（在线主路径·必有）：默认部署（外网可达 Astral CDN / GitHub Releases）触发目标版本首跑 → 动态下载成功。
- AC-NFR14b（可选·镜像）：启用 `UV_PYTHON_INSTALL_MIRROR` 的部署（无外网、仅内网镜像可达）→ 动态下载从镜像成功。
- AC-NFR14c（可选·离线预填）：仅离线预填缓存卷（无外网无镜像）→ 命中缓存执行成功；未预填版本首跑 → 任务失败且分因 `interpreter_unavailable`（明确失败，见 D14）。

**NFR-15**：**[v0.3 修订]** 解释器缓存池（`UV_PYTHON_INSTALL_DIR`）须纳入磁盘回收模块范围：**解释器层默认豁免常规 TTL 清扫**（解释器为可复用资产，避免重复下载），改用**体积红线**治理——默认单版本 ≤250MB、缓存池总占用 ≤4GB；超限触发告警并回收最久未使用版本（默认策略，见 D12）。下载大小与带宽须量化并计入部署容量规划（Each 下载 → 记录）。
- AC：缓存池单版本/总池达红线 → 告警 + 最久未使用版本回收生效；TTL 用例不删除解释器层（豁免验证）。
- AC：部署容量规划文档含缓存池体积测算（版本数 × 单版本体积预估）。

**NFR-16**：**[v0.3 修订]** 同一执行器上多个任务并发首次请求同一解释器版本的下载须互斥进行。默认机制：**per-version 锁 + 全局单下载队列**（同一时刻全局至多一个 in-flight 解释器下载；同一版本锁保证该版本仅下载一次），等待者阻塞等待下载完成后就绪复用，不得重复下载或产生缓存目录写竞争（见 D13）（When 并发 → 互斥）。
- AC：并发触发两个声明 3.9 的任务 → 3.9 解释器仅下载一次，两任务均以同一缓存解释器建 venv 并行成功运行。

## 6. 约束与假设（CON / ASM）

**CON-01**：executor-python 镜像基座维持 `python:3.12-slim` 运行执行器本体（其依赖要求 ≥3.8）；执行器依赖基准线不变。多版本解释器能力由**执行器内置 uv 按需动态下载**实现，不改变执行器本体依赖，不新增镜像预装解释器层。

**CON-02**：**[v0.3 修订]** 任务运行解释器 = 执行器本地缓存池（`UV_PYTHON_INSTALL_DIR`）中按任务声明动态获取的**任意受支持版本**解释器（模型从"唯一宿主默认"扩展为"按任务声明动态获取"），仍不把任务运行解释器与执行器本体解释器混淆。

**CON-03**：上传 zip ≤200MB 限制沿用现有 `POST /applications/upload`；不另开上传点。

**ASM-01**：**[v0.3 修订]** **解释器按需在线下载为本需求主路径**：执行器通过 `uv python install <version>`（或 `uv venv --python <version>` 的自动下载语义）在任务准备阶段下载 python-build-standalone 构建的 CPython 解释器（受支持区间内任意版本）并缓存复用；镜像预装不再是 G2 达成的必要条件。在线主路径所有部署必有。

**ASM-02**：**[v0.3 修订]** 受支持区间内任意版本解释器来源为 uv 下载的 python-build-standalone 构建产物（Astral 维护）。已知边界事实：3.7 系列构建止于 **3.7.9**（Tier 2 下界附近）。区间**上下界**可用性均受 uv 版本冻结影响（见事实 11），须经 D10 验收项实测 `uv python list --all-versions` 确认后明示支持矩阵。

**ASM-03**：**[v0.3 修订]** uv 0.8.17 须支持按需下载受支持区间内目标版本解释器并以其创建 venv（Tier 2 政策下旧版本预期可用）；若 D10 实测完整区间与本文支持矩阵（3.6~3.14）不一致，该条件升级为阻塞性问题：须升级/调整 uv 版本并重新锁定执行器依赖后再次验证。

**ASM-04**：执行器宿主可写盘空间满足解释器缓存池 + 任务 venv + 解压目录共存（结合 NFR-12/NFR-15 磁盘红线，默认总池 ≤4GB）。

**ASM-05**：任务与执行器之间的版本匹配以"执行器上报的解释器清单（启动时 `uv python list --only-installed` 的缓存结果）"为准，派发链路不依赖执行器侧实时探测/实时下载（避免派发引入网络 IO）；运行时获取失败由 FR-08 兜底。

**ASM-06**：**[v0.3 修订]** 存量项目（含任意受支持版本）所需依赖可用私有 PyPI（registry-pypi）提供；若依赖自身已不在任何源的所声明版本兼容区间，平台无法代为解决（超出本需求能力边界）。

**ASM-07**：**[v0.3 修订·新增]** 私有化/离线部署为**可选部署模式**而非全局硬约束：默认部署仅依赖在线动态下载主路径；部署方按需启用 `UV_PYTHON_INSTALL_MIRROR` 或离线预填缓存卷（配置方式与生效校验文档化）。未启用可选模式且外网不可达时，动态下载不可用，仅能运行缓存中已有版本，任务失败分因为 `interpreter_unavailable`。

## 7. 非目标（Non-Goals）

| 编号 | 非目标 |
|---|---|
| **NG-01** | 不做任务代码的自动构建/打包（用户自行将项目打成 zip 上传）。 |

| **NG-09** | **[v0.3 修订·新增]** 不支持受支持版本区间之外的解释器版本（<3.6、>3.14 及 uv 政策外版本）；解释器仅来自缓存池受控下载，不做区间外承诺；不承诺验证每个补丁号（仅到主.次版本粒度，见 D1）。 |

## 8. 验收要点（汇总清单）

> 完整验收点已随各 FR/NFR 附于上文（AC-xx）。此处仅列系统级端到端验收主线，供发布门禁（Release Gate）使用。

## 9. 关键技术决策点

**[v0.3 修订]** D8/D9 按"uv 动态下载 + 缓存池 + 在线主路径/可选私有化模式"定稿；D10 扩展为"完整可下载区间（含上下界）实测与支持矩阵明示"；新增 §9.2 授权默认决策值（D11~D14，负责人授权的"其余自行决策"项，标记【默认值】）。D1~D7 已按既有建议落定默认值，不再阻塞。

### 9.1 决策点表

| 编号 | 决策点 | 选项 | 建议 |
|---|---|---|---|
| **D1** | **版本匹配语义** | ① 精确匹配（3.7==3.7）；② 前缀匹配（3.7 匹配 3.7.x）；③ 范围匹配（`>=3.7,<3.8`） | ②前缀匹配（主.次精确、补丁号不敏感），范围匹配作为后续演进；本期不引入运算符语法。 |
| **D2** | **版本不满足时的报错时机** | ① 仅调度过滤（派发失败）；② 创建/编辑任务时预警；③ 运行前拦截（含 pinning 场景） | 三层并发：创建时预警 + 调度过滤 + 运行前硬失败兜底（尤其 executorId pinning 场景必须在运行前报错）。 |
| **D3** | **任务版本字段承载** | ① 复用 `tasks.runtimeVersion` 并赋予执行语义；② 新增专用字段 | ①复用 `runtimeVersion`（已存在、命名贴切、无迁移新列），仅需文档化语义与执行器契约。 |
| **D4** | **zip 依赖与任务 requirements 合并规则** | ① 并集安装（包内∪任务）；② 任务覆盖包内同名依赖；③ 仅任务 requirements 生效（包内忽略） | ② 任务级优先覆盖同名，其余并集；去重由 uv 同期锁定保证幂等。 |
| **D5** | **解释器清单上报载体** | ① 复用 `executors.capabilities`（如 `python:3.7` 标签）；② 新增 `interpreters` 数组字段 | ② 新增 `interpreters` 结构化数组（版本/路径/可用态），避免污染 capabilities 的标签语义；旧执行器无此字段视为 `["3.12"]`。 |
| **D6** | **venv 目录键签名** | ① `taskId`（现状）；② `taskId-<版本>` | ② `taskId-<主.次版本>`，切换版本生成新 venv（同 FR-16）。 |
| **D7** | **zip 包与任务的关联模型** | ① 复用 `tasks.applicationId` 弱引用 + `runtime`=识别；② 新增任务 `sourceType`/`sourceRef` 字段 | ① 复用 `applicationId`（已存在）+ 新建 `codeSource` 枚举区分 `git\|glue\|application_zip`，语义最清晰且避免与 gitRepo/glue 三选一歧义（见 FR-18）。 |
| **D8** | **解释器获取与缓存方式** | ① **执行器内置 uv 按需动态下载**：`uv python install <version>` 下载 python-build-standalone CPython（受支持区间内任意版本）进入本地缓存池（`UV_PYTHON_INSTALL_DIR`），`uv venv --python <version>` 建 venv，多任务复用同一缓存解释器层；②（弃用）镜像预装多解释器——镜像体积、EOL 源可用性均不满足 | ① 作为主路径（平台执行器已内置 uv 0.8.17，见约束前提事实 13），配合 D9 可选私有化模式与 D10 版本冻结验证。 |
| **D9** | **解释器获取通道（在线主路径 + 可选私有化模式）** **[v0.3 修订·改写]** | ① 主通道：Astral CDN / GitHub Releases（uv 默认下载源），**所有部署必须可用（默认主路径）**；② 可选部署配置 A：`UV_PYTHON_INSTALL_MIRROR` 内网镜像；③ 可选部署配置 B：部署期离线预填解释器缓存卷（预先导入 `UV_PYTHON_INSTALL_DIR`） | ① 为**在线默认主路径，全局必有**；②/③ 为**部署方可按部署模式选择启用的可选配置**，不构成全局硬约束，配置与生效校验文档化。未启用 ②/③ 且外网不可达时，动态下载不可用，仅能运行缓存中已有版本，任务失败分因 `interpreter_unavailable`（降级语义见 D14）。 |
| **D10** | **uv 版本冻结与可下载版本完整区间验证** **[v0.3 修订·扩展]** | 现状：执行器依赖锁定 uv 0.8.17；uv 对每个发布版本**冻结可下载版本列表**。验收动作：隔离环境实测 `uv python list --all-versions`（uv 0.8.17），确定**完整可下载版本区间（含上下界）**，据此**明示本文支持矩阵**（预期 3.6~3.14，Tier 1 = 3.10~3.14 / Tier 2 = 3.6~3.9）；已知边界：3.7 构建止于 3.7.9 | 分岔处理：区间与支持矩阵一致 → 维持 0.8.17 并固化支持矩阵；不一致（如缺下界版本或上界不足）→ 升级 uv 版本或自定义下载镜像并重新锁定执行器依赖。**该验证为 G2 达成的阻塞性前置验收项，须先于其他实现工作完成。** |

### 9.2 授权默认决策值（v0.3，负责人授权"其余自行决策"项）

> 以下四项按负责人授权给出【默认值】直接写入，均标注可调依据；不再作为阻塞问题。若验收或部署反馈需调整，走配置化变更。

| 编号 | 决策点 | 【默认值】 | 可调依据 |
|---|---|---|---|
| **D11** | **首次解释器下载超时预算** | **单次解释器下载独立超时默认 300s**；与任务总超时约束取较小者生效（归入任务超时预算模型，见 NFR-13）。 | python-build-standalone 单版本压缩包约 20~50MB 量级，常规局域网/公网 300s 充足；弱网/跨境现场可下调（如 120s）或上调，按部署网络情况配置。 |
| **D12** | **缓存池磁盘 TTL/体积红线** | **解释器层豁免常规 TTL 清扫**（复用资产避免重复下载），改用体积红线：**单版本 ≤250MB、缓存池总占用 ≤4GB**；超限 → 告警 + 回收最久未使用版本（纳入磁盘回收模块，见 NFR-15）。 | 单版本 ≤250MB 覆盖 python-build-standalone 解压后基座；总池 4GB 约可容纳 10+ 版本；磁盘富余现场可上调，受限现场下调并同步部署容量规划。 |
| **D13** | **并发首次下载互斥** | **per-version 锁 + 全局单下载队列**：同一时刻全局至多一个 in-flight 解释器下载；同一版本锁保证该版本仅下载一次；等待者阻塞等待完成后复用缓存（见 NFR-16）。 | 队列模型规避多版本并发下载打满带宽；如需提升多版本批处理吞吐可放宽为"每版本一个 in-flight"，默认取保守模型。 |
| **D14** | **镜像/离线模式下解释器不可用的降级语义** | **明确失败**：分因 `interpreter_unavailable`，不无限等待、不回退宿主解释器（版本语义为硬约束，回退将掩盖版本不匹配问题）；等待仅限并发同类下载（受 D13 约束）（见 NFR-14）。 | 若未来需要"降级到最接近可用版本"类能力，属于新需求，需显式评估语义风险后另行决策，本期不做。 |
