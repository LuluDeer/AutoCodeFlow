# 「自动补入队」（backlog auto re-enqueue）判定判据

> R216 立项。**先定判据，再写代码**（R388）。按 R393 的纪律：**先列「候选信号 × 它会被什么打穿」**。
>
> 状态：**已落地并真机验证**（R216 实现 + R217 端到端）。

## 1. 要解决的缺陷

`backlogged`（积压）= 会话是 `pending` 但队列里**没有任何指向它的 job**（R201/R215）。
这种会话**永远不会被执行**，而且**没有任何东西会自己修复它**：

- `sweepStaleRunning` 只扫 `running`（它不碰 `pending`）；
- GAP-3 的自动续跑只处理 `waiting_input(auto_resume)`（它不碰 `pending`）；
- 唯一的修复路径是**人点徽标 → 看说明 → 手工重新入队**（`BacklogBadge` 的 `onJump`）。

⇒ 夜间/周末无人值守时，一批 `queue.add` 失败的会话会**一直躺着**直到有人上班。

### 1.1 为什么现在才敢做（R215 的前置）

R215 修掉了积压判据的一处**误报**（`jobId === session.id` 只对首跑成立 ⇒ resume 入队的正常会话
被判成积压）。**在误报存在时做自动补 = 把观测缺陷放大成真副作用**（给正在正常排队的会话再补一条 job）。
⇒ 自动补的**前提**是「判据的误报率足够低」。R215 之后，积压判据在已知路径上**只剩漏报风险**
（读不到 ⇒ 跳过 ⇒ 不补），这是**安全方向**。

## 2. 候选信号 × 它会被什么打穿（R393 的强制步骤）

| 决策点 | 会被什么打穿 | 结论 |
|---|---|---|
| 补什么 | 「积压」判据本身 | ✅ 复用（R201/R215，已修误报） |
| **谁补** | 多副本同时跑 ⇒ N 个副本各补一条 | ❌ 必须**单赢家**（见 §3.1） |
| **补几次** | 无限补 ⇒ 队列被同一条会话刷爆 | ❌ 必须**有上限且持久化**（见 §3.2） |
| **怎么防反复补** | 「补了但队列还是查不到」（例如 add 成功但被立刻失败）⇒ 下一轮又判积压 ⇒ 再补 | ❌ **计数必须落库**，不能只看队列（见 §3.2） |
| 补的动作 | 直接 `queue.add` 还是走既有 resume 路径 | ✅ 走**专用入口**（见 §3.3） |

## 3. 判据

> **自动补 = 对每条「判定为积压」且「`backlogReenqueueCount < 上限`」且「非终态」的会话，
> 以 CAS 领取一次额度后，用 `jobId = session.id` 入队一次。**

### 3.1 「谁补」：CAS 单赢家（**照抄 `claimAutoResume` 的纪律**）

`agent-session.service.ts:850` 的 `claimAutoResume` 已经是这个模式：

```sql
UPDATE agent_sessions SET "backlogReenqueueCount" = "backlogReenqueueCount" + 1
WHERE id = :id AND "backlogReenqueueCount" < :limit AND status NOT IN (:...terminal)
```

- **`affected > 0`** 才算赢得本次额度（多副本只有一个赢家）；
- **`status NOT IN (terminal)`** —— 会话可能已被别的路径收敛（人工 abort / 预算触顶），
  此时补一条 job 毫无意义，命中 0 行就如实让位；
- 这条与 ADR-026（条件写）、GAP-1（`markRunning`）是**同一条纪律**。

### 3.2 「补几次」+「怎么防反复补」：**计数落库**，上限 1

**上限 = 1**（与 `claimAutoResume` 的默认 `max=1` 一致）。理由：

- 一条会话若补了一次仍然「积压」，说明**不是瞬时失败**（`queue.add` 又失败 / job 被立刻清理）
  ⇒ 再补只是重复撞同一堵墙 ⇒ **交给人**；
- 上限 1 让「自动补」的**最坏副作用**被封顶：最多多一条 job（且 `jobId = session.id` 幂等）。

⚠️ **为什么计数必须落库、不能只看队列**：
「补了但队列里查不到」有两种成因 —— ① add 失败（该重试）；② add 成功但 job 被消费/清理
（**不该**再补）。只看队列**分不开**这两者，而落库的计数**记得**「我试过」。
⇒ 计数是**唯一**能区分「还没试过」与「试过但没用」的载体。

### 3.3 补的动作：专用入口，**不复用 resume**

不走 `POST /sessions/:id/resume`（它有一串额外闸门：`succeeded`/`aborted` 拒绝、
`running` 409、pending 审批拒绝、`budget_exceeded` 拒绝）。理由：

- 那些闸门是**人工动作**的语义（人决定「再看一眼」时不该绕过审批）；
- 自动补是**无状态修复**，它只需要「`pending` 且无 job」这一个前提（判据已保证）；
- 两者混在一起会让「为什么自动补失败」变成一个要读 5 个 if 才能回答的问题。

⇒ 入队用 **`jobId = session.id`**（与首跑同形态 ⇒ **积压判据能直接查到它**，R215 的教训）。

### 3.4 与其它自动处置的对照（R399 的强制步骤）

| 自动处置 | 对象 | 为什么可以做 / 不可以做 |
|---|---|---|
| `sweepStaleRunning` | `running` 但久无进展 | 可以（那个状态下**本来就没有**正常路径在推进它） |
| GAP-3 自动续跑 | `waiting_input(auto_resume)` | 可以（LLM 瞬时错误，重试是正确动作） |
| **自动补 enqueue（本条）** | `pending` 且**无 job** | 可以（**没有 job 就永远不会跑**，补一条是唯一恢复路径；且 `jobId` 幂等） |
| ~~自动改 `failed`~~ | — | **不可以**（会让运营只能走 resume，多一步且有限制） |
| ~~自动 resume~~ | 见 §3.3 | 不可以（会绕过审批门） |

## 4. 动作：**自动处置，但副作用被封顶**

与其余五条判据（只告警不处置）**不同** —— 因为「不处置」的后果是**该会话永远不会跑**。
但副作用必须被封顶：

1. **最多补 1 次**（计数落库）；
2. **`jobId = session.id` 幂等**（重复 add 是 no-op）；
3. **不碰会话状态**（不改 `status`、不动预算、不动审批）；
4. **不补有 pending 审批的会话**？—— **要补**。`pending` + 有审批单是矛盾的
   （审批意味着 `waiting_input`），但如果真出现，补一条 job 让它去处理审批是**正确**的
   （`run()` 会看到审批并让位）。⚠️ 这一条**需要用例钉住**，不能只靠推理。

## 5. 已知边界（**如实登记**）

- **判据误报的兜底**：若积压判据将来又出现误报（例如再加一条入队路径），自动补会
  **真的**多补一条 job。缓解：`jobId = session.id` ⇒ 与首跑**撞 id** ⇒ BullMQ 幂等 no-op
  （若首跑 job 还在）；但若首跑 job 已被消费（`completed`）而会话仍 `pending`，
  补的那条会**真的**再跑一遍 —— 这正是「积压」的定义（job 已终结而会话仍 pending），
  也是 R201 判据认为「该补」的情形。
- **扫描上限**：复用 `BACKLOG_PROBE_LIMIT = 200`；超出的部分**不补**（`truncated` 时也在
  响应里说明了）。⇒ **一次最多补 200 条**。
- **不补偿「补的时候 Redis 正好挂了」**：`queue.add` 抛错 ⇒ 本次放弃（**计数已经 +1**，
  因为 CAS 在 add 之前）。这是**刻意的**：宁可少补一次也不制造重试风暴。
  ⚠️ 代价：一次 Redis 抖动会让那批会话**永久**失去自动补资格（只能人工）。**如实登记。**
  ⇒ 缓解见 §5.1。

### 5.1 CAS 与 add 的顺序：为什么先 CAS 后 add（而不是反过来）

- **先 add 后 CAS**：两个副本会各 add 一条（幂等 ⇒ 无害），但**都**在 add 之后才 CAS ⇒
  其中之一失败 ⇒ 计数与事实不符；
- **先 CAS 后 add**：只有一个副本进入 add；若 add 失败，计数已 +1（**少补**）。

⇒ 选**先 CAS 后 add**：**少补**（漏报）比**多补**（重复执行）安全 ——
与 R210/R212 建立的「误报代价 > 漏报代价」同一条纪律。

## 6. 日志的**三态**（R217 真机发现的可观测性缺陷，已修）

原实现只在 `attempted > 0` 时打日志 ⇒ 把两种**完全不同**的情形压成了同一个「静默」：

| 情形 | 含义 | 应该有信号吗 |
|---|---|---|
| `candidates === 0` | 真的没有积压 | **不需要**（每 10 分钟一条「什么都没发生」会淹掉日志） |
| `candidates > 0 && attempted > 0` | 正常补了 | 需要（`log`） |
| **`candidates > 0 && attempted === 0`** | **有积压但一条都补不动**（均已补过 / 状态已变） | **需要（`warn`）** |

第三态被静默的后果：运营看到徽标上的数字**一直不变**，却**不知道为什么**
——「自动补明明在跑，为什么没效果？」没有任何日志能回答。
这正是本仓主导缺陷类（「有问题」被渲染成「什么都没发生」）的又一形态。

⇒ 现在：`candidates === 0` 静默、`attempted > 0` 打 `log`、**`attempted === 0 && candidates > 0` 打 `warn`
并明说「自动补帮不上忙，需要人工介入」**。

## 7. 端到端验证（R217）

`npm run test:r217-auto-requeue-e2e`（真 cron + 真 Redis + 真 PG，**会真的等两轮 cron，最坏约 22 分钟**）：

| # | 断言 |
|---|---|
| ② | 造真积压 ⇒ `/backlogged` **能识别它**（判据前提成立） |
| ③ | **真 cron 触发**（不手动调 `runOnce()` —— 那会跳过「注册/触发」这一层，R416 的教训） |
| ④ | 真 Redis 里出现 `jobId = session.id` 的 job（形态正确，R215 的教训） |
| ⑤ | `backlogReenqueueCount` = **1**（CAS 生效） |
| ⑥ | **闭环**：`/backlogged` 不再报它 |
| ⑦⑧ | **幂等**：`count` 已=1 的会话 ⇒ 下一轮**不产生 job**、计数**仍为 1** |

⚠️ **本探针自己也踩过一次坑（R407 同型）**：③ 首版只匹配「含 `attempted=1` 的行」，
而隔离 Redis 复用时会命中**上一轮**留下的旧日志行 ⇒ ③ **假绿**、而 ④⑤⑥ 全红。
修法：日志行自带结构化 `timestamp` ⇒ 只认 `sinceMs`（本会话插入之后）的行。
**这就是「探针红了先问红的是产品还是探针」的实际用例。**
