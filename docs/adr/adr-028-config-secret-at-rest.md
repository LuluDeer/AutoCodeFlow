# ADR-028：配置类密钥的静态加密边界

- 状态：**接受现状（有明确触发条件）**
- 日期：2026-10-20
- 相关：ADR-025（审计不可篡改）、SEC-02（任务密钥静态加密）、R83（配置写动作落审计）

## 背景

平台里有三类「密钥」：

| 类别 | 存放 | 静态加密 |
|---|---|---|
| **任务级密钥**（task.secrets） | `tasks.secrets` jsonb | **有**（SEC-02，`enc:v1:` 信封，`SEC_SECRETS_KEY` 缺失时降级为明文并 warn） |
| **平台级配置密钥**（`isSecret: true` 的 system_config 行，如 `executor.sharedToken` / SMTP 口令 / Webhook 签名密钥） | `system_config.value` | **无** |
| 同一批配置的历史值 | `config_history.oldValue/newValue` | **无**，且每键保留 50 条 |

R83 顺着「密钥脱敏」这条线走到持久化面时确认了这个落差：**平台级共享口令（`executor.sharedToken` 决定集群内
所有执行器的鉴权）恰恰是明文落库的那一类，而且同一份明文在 `config_history` 里有最多 50 份拷贝。**

## 决策

**接受现状**：不在此刻为 `config_history` 单独加密。理由不是「成本高」，而是**那样做是安全剧场**：

> 只把**历史副本**加密、让**现值**继续明文，攻击者读 `system_config` 一行就拿到全部内容。
> 多出来的只有一句「历史是加密的」的错觉，却多出「同一密钥两种存储形态」的一致性负担
> 与一条容易写错的解密路径（rollback 必须能读回它）。

真正的修复是把**现值**加密（`system_config.value` 对 `isSecret` 行走 `enc:v1:` 信封），代价与阻塞点都很
具体：

1. `ConfigService.get/findAll` 的**所有读点**都要解密（含进程内 TTL 缓存、跨实例失效广播、健康检查、
   `executor.sharedToken` 这类**启动期**读取方）；
2. **rollback** 要从历史恢复，历史也必须同格式，否则回滚会把信封写进现值；
3. 存量行是明文，需要一个「首次读取时升级」或迁移；降级模式（无 `SEC_SECRETS_KEY`）下必须**行为逐字节
   不变**——否则一次部署就把所有配置读空；
4. 密钥轮换与「换了 key 但旧信封还在」的共存期，SEC-02 目前也没有解决（见其 `enc:v2:` 预留）。

这些都不是不能做，但它们合起来是**一次数据结构变更**，不适合夹在别的修复里顺手做。

## 现状下的补偿控制（真实存在的，不是安慰）

- **读面掩码**：`ConfigController` 对 `isSecret` 行与历史行都返回 `***`；编辑表单回传 `***` 时被解析回真值
  （S3 / R32-A2 的哨兵语义），不会把掩码写进库。
- **不可篡改的写留痕**：R83 起 `config.create` / `config.update` / `config.delete` 进 `audit_logs`
  （append-only，触发器拒绝 UPDATE/DELETE），detail 只记 `valueType` / `isSecret` / 长度，**不记值**。
  在此之前，「谁改过 sharedToken」只能靠 `config_history` 那行**会被保留期清理**的记录回答。
- **保留期**：`config_history` 每键 50 条 + 每日 04:05 清理；历史值不会无限堆积。
- **部署面**：数据库凭据按最小权限授予应用账号（见 `docs/DB-LEAST-PRIVILEGE.md`），
  「能读 DB」本来就等价于「能读全部配置」。

## 触发条件（满足任一即重开并实施「现值加密」）

1. 出现**多租户 / 多环境共库**的部署形态（DB 读权限不再等于「平台自己」）；
2. 合规要求落成条款（等保 / SOC2 之类明确要求「密钥不得明文落库」）；
3. `SEC_SECRETS_KEY` 变成**必配**项（不再有降级模式）——那时现值加密的兼容成本最低；
4. 出现「历史表被单独导出/共享」的运维场景（此时历史副本的暴露面**高于**现值）。

## 后果

- **明确接受了什么**：DB 读取者可见平台级配置密钥的明文，且历史上最多 50 份拷贝。
- **明确没有做什么**，以及为什么：不为历史表单独加密（安全剧场）、不在本轮做现值加密（数据结构变更，
  需要独立的兼容/迁移/降级设计）。
- **接口预留**：`SecretsCryptoService` 的 `encryptValue` / `decryptValue` 与 `isEncryptedSecret` 已就绪，
  未来对 `system_config.value` 加密时可直接复用同一信封格式与降级语义。

## 替代方案（被否）

- **只为 `config_history` 加密**：见「决策」——现值仍明文，收益为 0 而复杂度与一致性风险为正。
- **把配置密钥迁进任务密钥那套存储**：两类东西的生命周期与读取方完全不同（配置要启动期读、任务密钥只在派发
  时读），强行合并会把启动路径变成「必须解密才能读 sharedToken」，放大降级模式的风险面。
- **缩短密钥类历史的保留条数**：会把 rollback 深度按「是不是密钥」切成两档，运维语义变复杂；
  且 50 份已经是有限的、每天都在清理的量级。
