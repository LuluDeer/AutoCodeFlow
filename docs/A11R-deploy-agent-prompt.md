# 部署端 Agent 提示词：A-11R 全量应用修复与重新发版

> 用途：把下面 **「提示词正文」** 整段复制给部署端 agent 执行。
> 平台侧修复已完成并落在 `develop`（协议 v5 / A-11R），本提示词负责**应用侧**的
> 审计、修复、验证与重新发版。

---

## 提示词正文

你是 AutoCodeFlow 的部署运维 agent。平台侧刚完成 **A-11R（协议 v5）** 修复，现在
需要你把这个修复**真正落到所有已部署应用上**并重新发版。请严格按下面的步骤执行，
**每一步都要给出真实证据**（命令输出、文件行号、执行记录 ID），不允许用"应该已经
修好了"这类推断替代验证。

### 一、背景：你要修的是什么（先读懂，再动手）

平台在 **2026-10-02** 上线过一个叫 **A-11** 的改动：任务 `params` 注入子进程环境
变量时，**每个值都先做 JSON 序列化**。它的本意是修复一个问题（布尔/空值/容器在两
个执行器上产出不同字节），但落地时**把字符串也一起序列化了**，于是：

| 你在中台里填的参数 | A-11 注入的环境变量 | 后果 |
|---|---|---|
| `region = 欧盟` | `AUTOFLOW_REGION='"欧盟"'` | 值里**多了一对首尾双引号** |
| `limit = 3` | `AUTOFLOW_LIMIT='"3"'` | `int(...)` 直接 `ValueError` |
| `mode =`（空串） | `AUTOFLOW_MODE='""'` | `'""'` 是**真值**，判断走错分支且不报错 |

**已知受害者**：`tk-ship-notify` 因为没做容错，`region_filter_formula('"欧盟"')`
抛「未知区域参数」→ 任务 failed → 运营在 **2026-10-02 ~ 10-14 收不到任何飞书通知**，
静默停摆 12 天。

**平台侧现在的状态（协议 v5 / A-11R）**：
- 逐键通道 `AUTOFLOW_<KEY>`：**字符串回归裸值**（`欧盟` 就是 `欧盟`，不加引号）；
  布尔/数字/数组/对象仍是 JSON 字面量（`true` / `3` / `[1,"a"]`）。
- 新增类型化通道 `AUTOFLOW_PARAMS_JSON`：整个 params 一份 JSON。**需要精确类型
  时读它**——逐键通道的值恒为字符串，原理上无法区分字符串 `"true"` 与布尔 `true`。
  该变量在 params 为空时**不存在**。
- 两个 SDK（`autoflow-sdk` / `@autocodeflow/sdk`）已改为**优先读类型化通道**并做
  类型还原，对旧执行器的引号形态也做了剥离容错。

**关键前提**：以上只在**执行器升级到协议 v5 之后**才生效。`protocolVersion < 5`
的执行器**仍然会加引号**（注意：A-11 上线时没有 bump 版本号，所以 **v4 同时存在
"加引号"和"不加引号"两种机队**——不能只靠版本号是 4 就断定行为）。

### 二、第 0 步：确认前置条件（不满足就不要往下做）

1. 确认中台已升级到包含 A-11R 的版本。
2. 对**每一台**执行器，查它的 `protocolVersion`（执行器详情页，或注册/心跳上报值）：

   ```bash
   # 中台 API 形态（按你的环境替换地址与令牌）
   curl -s -H "Authorization: Bearer $ACF_TOKEN" \
     "$ADMIN_API/api/executors" | jq '.data.list[] | {id, address, protocolVersion, version}'
   ```

3. 把机队分成两组，**分开处理**：

   | 分组 | 判据 | 该组的应用能否立刻恢复正常 |
   |---|---|---|
   | A 组 | `protocolVersion >= 5` | ✅ 能（字符串已裸值） |
   | B 组 | `protocolVersion <= 4` | ❌ 不能（仍加引号；v4 内两种行为并存） |

   **B 组的执行器必须先升级**（升级包 / 重装 / 换发布版本，按你们的既定流程）。
   在 B 组升级完成前，B 组上的应用**必须保留容错层**（见第三步的 `_unwrap`）。
   如有执行器**无法升级**，在最终报告里单独列出，并说明这些机器上的应用如何处理。

### 三、第 1 步：升级两个 SDK

应用读参数的推荐路径是 SDK，而旧版 SDK 对引号无感。请确认每个应用用的 SDK 版本
不低于含 A-11R 的版本：

- Python：`autoflow-sdk`（`pip show autoflow-sdk` 看版本；升级到含 A-11R 的版本）
- Node：`@autocodeflow/sdk`（`npm ls @autocodeflow/sdk`）

升级后行为变化（**这是本次修复对应用最直接的影响**）：
- Python `TaskContext.from_env()`：`ctx.params` 现在带**真实类型**（`True` 是布尔、
  `3` 是整数、嵌套结构保持结构），不再是清一色字符串。
- Node `TaskContext.fromEnv()` / `ctx.getParam(key, fallback?)`：优先读类型化通道，
  返回真实类型。

> ⚠️ **升级 SDK 后必须回归应用的参数读取逻辑**：以前 `ctx.params["flag"]` 恒为字符串
> `"true"`，现在可能是布尔 `True`。任何 `== "true"`、`str(v)`、`f"{v}"` 比较都可能
> 因类型变化而行为改变。**逐处核对，不要假设兼容。**

### 四、第 2 步：逐个应用审计并修复

对**每一个**已部署应用，执行下面的审计。不要抽样，不要"看起来没事就跳过"——
本次事故的本质就是静默失效。

#### 4.1 找出所有读参数的地方

```bash
# 应用仓库内
grep -rn "AUTOFLOW_\|os.environ\|process\.env\|get_param\|getParam\|params\[" --include=*.py --include=*.js --include=*.ts .
```

**特别当心这两类容易被漏掉的写法**（`tk-ship-notify` 就是栽在第二类）：
1. 有 `_unwrap` 的应用里，`_env` / `_env_bool` / `_env_int` / `_env_list` / `_env_json`
   是否**全部**经过了 `_unwrap`；
2. **绕过 `_env` 的手写读取函数**（例如为了保留"设了但为空"语义而直接读
   `os.environ` 的 `_read_region` 之类）——这类函数**必须单独调用 `_unwrap`**，
   这是最容易漏的一处。

#### 4.2 每个应用按下面的判据决定怎么改

| 应用所在执行器 | 应用的读取方式 | 处理 |
|---|---|---|
| A 组（≥ v5） | 读裸值 / SDK | ✅ 无需改动；**验证即可**（第四步） |
| A 组（≥ v5） | 自己做了 `json.loads` 解析 | ⚠️ **必须检查**：v5 下字符串是裸值，`json.loads("欧盟")` 会**抛异常**。改为「能解析才解析」的容错形态，或直接读 `AUTOFLOW_PARAMS_JSON` |
| A 组（≥ v5） | 有 `_unwrap` 容错层 | ✅ **保留即可（无害）**：裸值不以引号开头，`_unwrap` 原样返回。可在确认全机队升到 v5 后再清理；**不要在升级完成前删** |
| B 组（≤ v4，未升级） | 无容错层 | ❌ **必须补容错**（见下），否则仍带引号；同时推动该执行器升级 |
| 任意 | 需要精确类型（布尔/数字/数组） | ✅ 改读 `AUTOFLOW_PARAMS_JSON`（注意缺失时回落逐键读法） |

**容错层参考实现**（给 B 组应用；A 组应用不需要新加）：

```python
def _unwrap(raw: str) -> str:
    """A-11 兼容层：旧执行器给字符串加了首尾 JSON 引号（空串是 '""'）。

    ⚠️ 只解一次。不要对同一个值重复调用（例如 _env_json 内部已解过，
    外层再解一次会把用户真的以引号开头/结尾的字符串吃掉）。
    """
    if len(raw) >= 2 and raw[0] == '"' and raw[-1] == '"':
        try:
            import json
            decoded = json.loads(raw)
            return decoded if isinstance(decoded, str) else raw
        except ValueError:
            return raw
    return raw
```

**精确类型的读法**（推荐用于所有需要区分 `"true"` 与 `true` 的场景）：

```python
import json, os

def get_params() -> dict:
    """优先读类型化通道；旧执行器缺失时回落逐键通道。"""
    raw = os.environ.get("AUTOFLOW_PARAMS_JSON")
    if raw:
        try:
            return json.loads(raw)
        except ValueError:
            pass
    return {}   # 回落：逐键 AUTOFLOW_<KEY> 读法
```

#### 4.3 特别检查：`secrets` 的旧通道

`secrets`（凭据）会被合并进 `params`，因此**按 `AUTOFLOW_<KEY>` 读凭据的老写法同样
受引号影响**（`AUTOFLOW_FEISHU_APP_ID='"cli_xxx"'`）。请检查：
- 应用若按**裸名**读凭据（`os.environ["FEISHU_APP_ID"]`）→ **不受影响**，无需改动；
- 应用若按 `AUTOFLOW_` 前缀读凭据 → 需要同样的容错，或改读裸名（推荐）。

### 五、第 3 步：验证（必须给真实证据）

对每个应用，**至少**做到：

1. **静态自检**：断言 A-11 形态的值能被正确解读——
   `'"欧盟"'` 能解出 `欧盟`，`'""'` 解出空串且**不等于**"未设置"。
   如果应用有 `selfcheck_offline` 之类的离线自检入口，把它跑通并贴输出。
2. **真实执行**：在中台**手动触发**该应用的任务，确认执行成功且业务结果正确
   （不只是"任务 success"——要确认业务动作真的发生了，例如通知真的发出去了）。
   **贴执行记录 ID。**
3. **边界复核**：对每个应用，明确回答"如果这个参数带引号，我的代码会怎样"。
   如果一个应用**当前 `params` 是空的**（因此还没暴露问题），也要检查：**一旦给它
   加任何字符串参数会不会静默失效**。
4. **输出验证矩阵**（每个应用一行）：

   | 应用 | 执行器 protocolVersion | 参数读取方式 | 改动 | 验证方式 | 证据（执行 ID / 输出） | 结论 |
   |---|---|---|---|---|---|---|

### 六、第 4 步：重新发版

1. 按你们的发布流程，重新发布所有有改动的应用（版本号递增，附 changelog）。
2. **发布后必须再跑一次真实执行**（不能只在发布前验证过就结束）——
   发布动作本身可能引入回归。
3. 记录每台执行器的最终 `protocolVersion`；**若仍有 B 组执行器**，在报告里明确列出
   它们的地址、所属应用、以及在升级前所依赖的容错措施。

### 七、红线与常见错误（务必避免）

- ❌ **不要**为了让报告好看而只跑"参数为空"的任务——那正是本次事故能潜伏 12 天的
  原因（params 为空时不注入，走默认值，看不出问题）。
- ❌ **不要**对会写生产的应用依赖"非法参数会提前失败"来兜底。验证时**先显式传只读
  参数并断言它**，确认链路通了再跑写操作。
- ❌ **不要**盲目给所有应用加 `_unwrap`：那是把平台缺陷变成租户负担（每个新应用都
  要重抄一遍）。正确顺序是**先升级执行器 → 再用 SDK / 类型化通道**；容错层只作为
  B 组升级完成前的过渡。
- ❌ **不要**在升级 SDK 后不做回归：参数类型从"全是字符串"变成"真实类型"，任何
  字符串比较/拼接都可能受影响。
- ❌ **不要**编造执行记录 ID、版本号或验证结论。**查不到就说查不到**，把未知项单独
  列成"需人工确认"，比一个假的"已全部修复"有价值得多。

### 八、最终交付物

一份报告，包含：

1. **机队清单**：每台执行器的 `address` / `protocolVersion` / 是否已升到 v5。
2. **应用清单**：每个应用的审计结论（改了/没改/为什么）、验证证据（执行 ID）、
   发布版本号。
3. **未解决项**：无法升级的执行器、无法验证的应用、需要人工决策的点——逐条列出，
   附上你判断的依据。
4. **反证**：至少举一个"如果我没改这里就会怎样"的具体推理（例如：某应用在 B 组
   执行器上会拿到 `'"欧盟"'`），证明你的审计真的覆盖到了这类形态，而不是走过场。

## 备注（给人看的，不要复制给 agent）

- 提示词里刻意**没有**列出具体的应用名清单：部署端 agent 应当自己从机队与应用列表
  推导出完整清单，而不是只修你点名的那几个。若你希望限定范围，在第二条开头补一句
  「本次范围仅限应用 X / Y / Z」。
- 提示词要求"先确认执行器版本"是因为：**A-11 当年没 bump 协议版本**，所以 v4 里
  两种行为并存。若你们的机队已全部升到 v5，第二、三步的时间会大幅缩短。
- 若你们的应用不通过 SDK 读参数（纯 `os.environ`），第三步的 SDK 升级可以跳过，
  但第四步的逐应用审计**不能省**。
