# AutoCodeFlow 深度代码审查

## 1. 结论

本轮确认 7 项应修复的问题：1 项 P1、6 项 P2。主要风险集中在管理凭据访问控制、执行结果可靠交付、终态并发保护和客户端会话/重试语义。已有测试通过，不能据此推断这些跨模块及异常时序路径正确。

本报告是代码审查交付，不包含业务修复。未执行攻击性验证、线上操作、数据库重建、依赖安装、提交或推送。

| 编号 | 优先级 | 问题 |
| --- | --- | --- |
| DR-01 | P1 | 普通登录用户可通过安装命令接口读取执行器共享凭据 |
| DR-02 | P2 | 执行器先停止回调循环，导致停机期间产生的回调丢失 |
| DR-03 | P2 | 失联执行扫描以无状态条件的 save 覆盖终态并重复释放槽位 |
| DR-04 | P2 | 前端退出登录不撤销服务端 refresh token |
| DR-05 | P2 | 执行器包推送读取未统一配置的 URL 键，生成相对下载地址 |
| DR-06 | P2 | 前端对非幂等请求自动重试，可能重复触发业务副作用 |
| DR-07 | P2 | refresh token 消费非原子，并发请求可同时完成轮转 |

P1 表示应优先修复的权限边界问题；P2 表示特定配置或时序下影响正确性、安全性或功能可用性的问题。本轮未确认 P0，不代表不存在未覆盖缺陷。

## 3. 架构与审查范围

### 3.1 系统结构

管理 API 使用 NestJS、TypeORM、PostgreSQL、BullMQ/Redis；负责用户认证、应用与任务管理、调度、执行器注册、执行回调、通知及包分发。管理前端使用 React，统一 API 客户端承担响应拆包、刷新 token 与错误重试。

Node/Python 执行器负责接收任务、准备运行环境、管理子进程、记录日志并上报结果。Electron 桌面端启动打包的 Node 执行器。CLI、MCP、Node/Python SDK 提供外部接入，npm/PyPI registry 承载私有包分发。

### 3.2 阅读重点

- admin-api：全局 guard、JWT/角色、refresh/logout、配置与共享凭据、任务及调度器、回调、执行器槽位、失联恢复、包推送、上传、出站 URL 校验、实体与迁移。
- executor-node：启动/停机、回调队列和失败持久化、任务 worker、执行/部署/更新/日志/配置路由、下载、路径限制、环境变量和进程清理。
- executor-python：认证、任务执行、回调和生命周期；registry-pypi 的认证入口。
- admin-web：认证状态、退出、刷新、重试、路由权限及接口契约；页面并未逐一做浏览器验收。
- desktop、CLI、MCP、SDK：凭据传递、配置、客户端协议和生命周期抽查。
- 部署与 CI：Compose、配置示例、流水线和迁移编排的静态审查。审查期间新增的 Windows CI 只核对差异范围，未重新执行。

这不是全仓每一行的形式化验证，也不包含外部依赖漏洞数据库扫描或线上部署配置证明。

## 4. 详细发现

### DR-01 [P1] 安装命令接口向普通登录用户返回共享凭据

**定位**：[executor.controller.ts](../apps/admin-api/src/modules/executor/executor.controller.ts) 第 319-348 行；[executor.service.ts](../apps/admin-api/src/modules/executor/executor.service.ts) 第 1343-1369 行；[roles.guard.ts](../apps/admin-api/src/common/guards/roles.guard.ts) 第 20-28 行。

**证据**：`GET /executors/install-cmd` 使用 JWT guard，但方法和控制器均没有 ADMIN 角色限制。RolesGuard 在无角色元数据时放行。`getInstallCmd()` 将 `executor.sharedToken` 同时放进返回的 `token` 字段和命令的 `--secret` 参数。因此仅删除返回对象的 token 字段不能消除暴露。

**触发条件**：存在有效的非管理员登录态，且配置了 `ADMIN_API_URL` 和非空共享 token；若缺少 URL，此方法先返回 503。前端隐藏入口不是后端访问控制。

**影响**：普通用户获得机器侧凭据。凭据是否仍可用于注册，以及能否直连执行器，分别取决于数据库轮转状态、执行器静态 token 配置和网络可达性。不能将所有部署均描述成已可直接执行任意任务；但跨越人类用户与机器认证平面的秘密暴露本身已经成立。

**修复建议**：立即为该方法增加 ADMIN 角色要求；统一安装命令与注册校验的共享凭据来源，避免 DB 轮转后仍下发旧环境凭据。长期可采用短时效 bootstrap 凭据。修复后评估历史暴露并协调轮转，不能只轮转数据库而遗留执行器静态凭据。

**验收测试**：普通用户 403、管理员按配置返回成功、未登录拒绝；DB token 轮转后安装链使用一致的有效凭据；不得通过其他响应字段泄露同一秘密。

**历史关系**：既有审查收紧了 config 的共享 token 读取接口，本项是另一出口的遗漏，不是重复报告已修复路由。

### DR-02 [P2] 停机顺序导致回调滞留内存后丢失

**定位**：[main.ts](../apps/executor-node/src/main.ts) 第 130-177 行；[callback.ts](../apps/executor-node/src/callback.ts) 第 51-61、219-248 行；[task-worker.ts](../apps/executor-node/src/task-worker.ts) 第 98-112 行。

**证据**：`gracefulShutdown()` 先调用 `stopCallbackThread()`，再 `stopAll()` 并等待运行任务最多 30 秒；退出前只有日志 flush，没有回调 flush。`pushCallback()` 只写内存队列，停止函数只置 `stopped = true`。既有落盘机制处理发送失败，不保证处理循环停止后新入队的条目。

**触发条件**：停止后回调循环已退出，此时 worker 停止或正在运行的任务结束并产生回调。循环当时在途的批次是否完成并不改变后续入队条目无人消费的问题。

**影响**：成功/失败结果未送达管理端，执行记录可能滞留 RUNNING。重启恢复可能把已经成功且产生副作用的任务判为失败；启用重试时存在再次执行的风险。并非每次停机必然丢所有回调，而是该窗口内缺少交付保证。

**修复建议**：先停止接单，再停止任务生产者并等待运行任务；保持回调消费者运行到 drain 完成，等待在途发送，最后将剩余条目持久化后退出。处理硬超时和落盘失败，并确保补发仍受管理端终态幂等约束。

**验收测试**：停机等待中任务成功、队列中任务取消、管理端断连、在途发送和硬超时场景，逐条断言结果已送达或可靠落盘。仅测试 stop 后 push 不足以证明完整停机流程正确。

**历史关系**：W-25 的崩溃兜底并不等于回调交付保证，本项是生命周期收尾缺口。

### DR-03 [P2] 失联扫描未原子抢占终态，可能覆盖成功结果

**定位**：[executor.service.ts](../apps/admin-api/src/modules/executor/executor.service.ts) 第 905-970 行，核心写入在第 957-965 行。

**证据**：`detectLostExecutions()` 读取候选执行后，将实体状态改为 FAILED 并 `execRepo.save(exec)`，随后无条件释放槽位。该更新没有以当前数据库状态为条件；此 cron 也没有 Leader 判断。

**可发生的交错**：扫描读取 RUNNING；正常回调随后写入 SUCCESS 并释放槽位；扫描继续保存旧实体的 FAILED 并再次释放槽位。多副本也可能读取同一候选并各自完成失败收尾。

**影响**：已确认成功的状态被覆盖，日志/错误信息不一致，执行器计数被重复递减。即使计数有零下限，仍可能错误扣减其他在跑任务占用的容量。真实并发复现本轮未执行。

**修复建议**：采用带非终态谓词的条件 UPDATE，并以 affected/RETURNING 决定是否释放槽位。状态转换和资源释放应作为一个一致的收尾协议；增加 Leader 门只能减少副本竞争，不能解决与正常回调的竞争。

**验收测试**：两个扫描器竞争只有一个成功转换；回调先成功后扫描不得改写；扫描先失败后迟到回调不得二次释放；槽位最终计数与仍运行执行数一致。

**历史关系**：其他恢复/回调路径已有条件更新保护，本项是未统一采用该约束的独立路径。

### DR-04 [P2] 前端退出仅清本地状态，服务端刷新会话仍有效

**定位**：[MainLayout.tsx](../apps/admin-web/src/layouts/MainLayout.tsx) 第 148-153 行；[auth.ts](../apps/admin-web/src/store/auth.ts) 第 43 行；[auth.controller.ts](../apps/admin-api/src/modules/auth/auth.controller.ts) 第 98-124 行。

**证据**：退出菜单仅调用 store 的 `logout()` 并跳转登录页。store 只清 token、refreshToken 和 user。后端已有 `POST /auth/logout` 以及 `revokeAllForUser()`，前端退出没有调用它。

**影响和前提**：退出前已被复制的 refresh token 在服务端仍可使用，直到过期或其他撤销发生。不能把这一点描述为本地清理失败；本地值确实被清除，缺失的是服务端撤销。

**修复建议**：显式退出先调用撤销接口，再清理本地状态，并避免并发刷新在退出后重新写入 token。撤销失败时仍可清理本地，但不能声称服务端会话已失效。后端当前撤销所有会话，需明确这与产品期望的单会话退出是否一致。不要在统一 401 拦截器中无条件调用 logout API，避免递归和误撤销。

**验收测试**：用户点击退出触发后端撤销；此前 token 无法再刷新；网络失败仍清理本地；退出与在途刷新竞争不恢复登录态。

### DR-05 [P2] 执行器包推送 URL 配置与既有部署配置不一致

**定位**：[executor-package.service.ts](../apps/admin-api/src/modules/executor-package/executor-package.service.ts) 第 250-254 行；[update-package.ts](../apps/executor-node/src/routes/update-package.ts) 第 70-79 行。

**证据**：推送方法读取 `ADMIN_API_BASE_URL`，默认空串，然后拼接 `/api/executor-packages/:id/download`。初审搜索未发现该键在配置定义、示例和部署文档中对应配置。执行器将下载地址交给 URL 解析，要求绝对 URL。

**触发条件**：未另行注入 `ADMIN_API_BASE_URL`，即便运维已按其他业务配置 `ADMIN_API_URL` 或 `API_BASE_URL`，本读取也不会自动使用它们。

**影响**：下载地址为相对路径，执行器拒绝更新，包推送功能失败。手工设置该键的部署不受此特定问题影响。

**修复建议**：统一使用已定义的对外 API 地址配置，规范尾部斜杠和 `/api` 前缀；缺少配置时在管理端明确报错。并补查推送鉴权和 DB 凭据轮转一致性，不应只修字符串拼接。

**验收测试**：标准配置生成正确的绝对地址；空配置显式失败；尾部斜杠和前缀不重复；管理端到执行器再到包下载的完整契约测试通过。

### DR-06 [P2] 通用错误重试会重发非幂等操作

**定位**：[client.ts](../apps/admin-web/src/api/client.ts) 第 119-125 行。

**证据**：客户端对网络错误或 5xx 自动重试一次，没有检查 HTTP method 或业务幂等能力。

**触发条件**：服务端已经接受任务触发/创建等请求，但响应在网络或代理层丢失，客户端看到网络错误或 502/504 后重发。错误响应不代表服务端没有执行。

**影响**：同一用户操作可能创建重复任务或重复执行。不是每个 POST 都一定有此风险，而是共享客户端无法证明这些操作可安全重试。

**修复建议**：默认仅对明确安全的读取操作重试；变更操作逐接口确认幂等语义。需要自动重试的触发接口应使用服务端幂等键，不能把客户端延时当作去重机制。

**验收测试**：模拟服务端已受理但返回网络错误，触发 POST 只发一次；读取请求仍可受限重试；启用幂等键时相同键返回同一业务结果。

### DR-07 [P2] refresh token 轮转存在检查与写入竞争

**定位**：[auth.service.ts](../apps/admin-api/src/modules/auth/auth.service.ts) 第 104-115 行。

**证据**：先读取 record 并检查 revoked，再设置 `record.revoked = true` 并 save，随后生成新 token。两个请求可以同时读取未撤销记录并都通过检查。

**影响和前提**：持有同一有效 refresh token 的并发请求可能各得到一套新凭据，破坏一次消费的轮转约束。该问题不会让无 token 的调用者凭空登录，但会放大已有凭据泄露后的会话分叉风险。

**修复建议**：使用 `WHERE revoked = false` 的原子条件更新，以受影响行数决定唯一消费成功者，并结合事务考虑新凭据签发失败时的行为。令牌家族复用检测可进一步加固，但不替代原子消费。

**验收测试**：对同一 token 同时刷新，仅一个成功；失败方不能生成新 token；正常单次刷新和过期/撤销拒绝逻辑不回归。

## 5. 次要观察与未计入缺陷的事项

以下内容不计入上面的 7 项，不应据此直接下结论为已证实漏洞：

- Node 心跳热重载：`routes/config.ts` 第 66-75 行更新配置，而 `scheduler.ts` 第 102-104 行在启动时固定 interval；应补证重载后是否存在重建定时器的其他入口，再修正热更新承诺或实现。
- `task.service.ts` 第 367-389 行：glue 更新与普通更新的调度同步收尾不同，需要围绕实际可修改字段补契约测试。
- 任务执行查询路由只按 executionId 查询：应验证路径 taskId 的一致性；当前任务共享权限模型下，不能直接声称存在跨租户越权。
- Compose 中数据库、Redis 和 registry 的宿主端口映射应按生产边界收紧。CI 测试凭据不能与生产泄密混为一谈；本轮未证明生产使用默认口令，也未核实防火墙暴露面。
- Desktop 凭据存储、IPC 路径参数和子进程环境继承值得专项加固，但未证明可由不可信远程输入到达，因此不报告远程任意文件读取或确定的凭据日志泄露。
- 初审对 registry Basic 解码分支提出疑点，但给出的样例不足以证明解码异常及绕过认证链，不纳入已确认发现。
- 版本历史写入调用链覆盖、SDK 的禁用降级语义等仍有专项测试空间；缺少调用搜索命中本身不等于确定的产品缺陷。

## 7. 建议修复顺序与验收原则

1. 先修 DR-01，并确认共享凭据各出口的权限及轮转一致性。生产是否轮转由维护者结合历史访问情况决定，本轮未做轮转。
2. 一并收敛 DR-02、DR-03 的执行结束协议：任务只终结一次、槽位只释放一次、回调可恢复交付。
3. 修 DR-04、DR-07 的会话生命周期，覆盖退出与刷新并发，而不只验证按钮跳转。
4. 修 DR-05、DR-06，增加标准配置下推送闭环和变更请求丢响应测试。

建议把角色矩阵、配置契约、并发交错、停机交付四类测试作为新增门禁。保持当前既有单元测试和 CI 守卫；不要用更多正常路径用例替代对这些异常状态的定向验证。
