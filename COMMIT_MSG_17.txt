feat(release): CLI 改名 @autocodeflow/cli 并接入发布链路 + 发布配置一致性守卫

问题：`acf-cli` 这个 npm 包名已被第三方占用（`npm view acf-cli` → 1.0.1，一个与本
项目无关的 NPM+Java 安装指南），直接 publish 必然 403。后果是 **mcp-server 与两个
SDK 都发了，唯独 CLI 从来发不出去**——它是同一套 API 的第三个入口，缺失让对外
交付面不完整。

改名（方案 A，用户已确认）：包名 → `@autocodeflow/cli`，用本仓已持有的
`@autocodeflow` scope（与 `@autocodeflow/sdk` 同 scope，归属确认：maintainer
kirdeer）。**`bin` 名保持 `acf` 不变**——终端命令改名会破坏既有脚本与操作习惯，
而 bin 名不必与包名一致。目录名 `packages/acf-cli/` 亦保持（仓库守卫与 root
scripts 都按目录引用，改名只会扩大改动面而无收益）。

修的过程中发现并修掉 4 个「配置写了一半」的真实缺陷（每个都只在真要发版时才暴露）：

1. **`acf-cli` 被 release-please 管理却永远不 bump**。它早在 a4dad9b 就写进了
   `release-please-config.json` 的 `packages`，却**漏进** `linked-versions.
   components`——于是被管着、却不参与 lockstep 版本提升，永远卡在 `1.0.0`。
   已纳入并统一 component 名为 `autocodeflow-cli`。

2. **`acf --version` 永远打印 1.0.0**（硬编码字面量）。而 `package.json` 才是
   version-guard 与 release-please 唯一会 bump 的地方，两者必然漂移。实测证据：
   包名/版本改成 1.4.3 后 `npx acf --version` 仍输出 1.0.0。改为读 package.json
   （单一事实源）。这是发布物里最不该骗人的一个输出——用户报 issue、我们判兼容
   性、脚本做版本分支读的都是它，且它装完就能立刻看到。

3. **测试文件被打进发布包**。tsc 会把 `src/__tests__` 一起编译进 dist，首版打包
   27 个文件含 3 个 `*.test.js`。**没有**用 tsconfig 的 `exclude` 修——那会连带让
   `npm run typecheck` 不再覆盖测试文件（`mcp-server` 正是这个盲区），改用
   `files: ["dist", "!dist/__tests__"]` 精准排除，两者兼得。

4. **`version-guard` 未覆盖 CLI**。已把这个第五处版本号纳入 lockstep 校验
   （发布矩阵同时加 `packages/acf-cli`）。

另：`projectName: 'acf-cli'`（决定 `~/.config/acf-cli/` 凭据目录）**刻意不改**——
它是用户机器上的持久状态，改名会让既有用户"莫名掉登录"，代价远大于收益。已在
代码里写明理由与将来若真迁移必须配套的一次性搬迁。

新增守卫 `scripts/check-release-config.mjs`（零依赖，含 4 个反例 selftest，已接入
CI 的 check-migrations job）。本仓发版链路跨**四份互不校验的配置**，任一处漏配都
不报错，只会让某个包静默地永远发不出去或永远不 bump——缺陷 1 就是这个形态。守卫
逐层校验：① packages 的 component 都在 linked-versions 里；② 发布矩阵的包都受
release-please 管理；③ 每个待发布包都在 version-guard 清单里；④ lockstep 组内版本
已一致。用**真实历史缺陷**验证有牙：把 `acf-cli` 从 linked-versions 移除 → 守卫
精确报出「该包会被 release-please 管理却永远不参与 lockstep 版本提升」。

新增 `packages/acf-cli/src/__tests__/release-metadata.test.ts`（8 条）：包名/scope/
bin/publishConfig 契约 + 打包不含测试 + 版本号不得硬编码，其中一条**真实执行构建
产物** `node dist/index.js --version` 比对 package.json（源码里写了什么不代表打出来
的包是什么），产物缺失时显式失败而非静默跳过——连带把 `npm run build` 提到 CI 的
`acf-cli-test` 测试步骤之前（同 admin-web 的 PERF-01 守卫约定）。

验证：acf-cli 112 passed / 1 skipped（+8）、mcp-server 113 passed（未受影响）、
`npm ci` 通过（lockfile 已同步新包名）、`typecheck:all` 7 工程 0 错、四个仓库守卫
全绿、docs-site sync-check 通过；并在**临时干净目录真实安装 tarball** 后跑
`npx acf --version` → 1.4.3、`npx acf --help` 十个子命令齐全，确认发布物可用。
