docs(handoff): 补记发版链路打通专项——6 个真实缺陷 + 2 条方法学教训

本轮从「CLI 改名接入发布链路」到「v1.5.0 四包全发布」，挖出并修复 6 个真实
缺陷，其中 4 个只在真正发版那天才暴露。逐个记录根因与修法（含钉到的源码
位置），避免重复排查：

① release-please 永久卡点——`manifest.ts:1146-1157` 只看 PR 的
  `autorelease: pending` 标签、**不看 tag 是否存在**；PR #4 标签停留在 pending
  而 v1.2.0 tag 已打 → 永久 untagged。把标签改回 tagged 即解除。
② acf-cli 漏进 manifest → Release PR 把它从 1.4.3 倒退到 1.0.0（上一轮
  「漏进 linked-versions」换了形态复发）。补条目 + 守卫加第 ⑤ 层。
③ e2e-full-windows 长期全红——venv 相对路径在 cd 之后失效，进程根本没起、
  空等 60s 超时。转绝对路径 + 启动前断言；修后用例 49 首次通过。
④ 文档站版本声明不在 release-please 管理面 → 每次发版必红，且
  docs-site-deploy 失败即不部署（文档站停更新）。加标记 + 登记 extra-files；
  顺带修表格版本号这一校验盲区。
⑤ PyPI Trusted Publishing 未登记 → publish-pypi 失败。登记步骤只写在 commit
  message 里，没人会翻。
⑥ SDK 发版抢占 GitHub latest → 全量装机用户桌面更新 404（每次 SDK 发版复发）。
  electron-updater 硬编码查 /releases/latest，无法指定 tag；两条 tag 线共用
  同一 Releases 池。新增 demote-sdk-release job 自动标 prerelease。

附 v1.5.0 发布结果（四包 1.5.0 + 文档站 1.5.0 + 自动打 tag 打通）与两条方法学
教训：
  1. 仓库外的手动步骤必须写进发版清单，不能只写进 commit message——本轮 ⑤⑥
     都是这个模式，且报错不指向缺失的那一步。
  2. 判定「修好了」必须看可观测事实而非 CI 绿——本轮多次遇到「CI 绿但没验证
     到」（job 被并发取消显示 skipped、rerun 后 PR 判定 remained the same 而
     没重算），都靠回到日志/API 逐条核对才定位。
